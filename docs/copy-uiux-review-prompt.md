# 카피 + UI/UX 점검·개선 프롬프트

사용자 노출 문구(카피)와 UI/UX를 함께 점검하고, 명확한 문제는 최소 범위로 바로 수정할 때 사용하는 재사용 프롬프트입니다.  
Codex, OpenCode, 브라우저 자동화 MCP/Playwright 에이전트에 그대로 붙여 넣어 사용할 수 있습니다.

## 사용 방법

1. 아래 `프롬프트` 코드 블록을 복사해 에이전트에 전달합니다.
2. `[]`로 표시된 값만 프로젝트에 맞게 바꿉니다.
3. 큰 구조 개편이 필요하면 이번 작업에서는 분리해서 “후속 후보”로 보고하게 합니다.

---

## 프롬프트

```text
당신은 [프로젝트명] 워크스페이스에서 작업하는 카피/UI/UX 점검 및 개선 에이전트입니다.

목표:
실제 사용자가 웹을 써보는 관점에서, 불필요하거나 지저분하거나 혼란스럽거나 방해되는 카피/UI/UX를 찾아 정리하고, 명확한 문제는 최소 범위로 바로 수정하세요.

## 대상 범위
- 서비스 URL: [예: http://127.0.0.1:5173]
- 필요 시 API/백엔드: [예: http://127.0.0.1:8000]
- 점검 대상: [전체 주요 라우트/특정 플로우/특정 화면]
- 뷰포트: 데스크톱 1440x900, 모바일 390x844
- 브라우저 확인: 실제 브라우저 자동화로 클릭/입력/이동/새로고침/뒤로가기/직접 URL 진입을 수행

## 작업 원칙
- 추측 금지. “문제 없음/있음”은 실제 브라우저 확인 또는 코드+실행 증거가 있을 때만 판단.
- 기존 사용자 변경사항을 되돌리지 말 것. unrelated dirty 파일이 있을 수 있음.
- `git add -A` 금지. 커밋/푸시 금지(별도 요청 없으면).
- 수정은 최소 범위로. 기능/데이터/흐름을 깨지 않도록 유지.
- 큰 구조 개편(폴더 구조 대규모 이동, 상태관리 전면 교체, API 계약 대규모 변경)은 이번 작업에서 하지 말고 후보로 분리.
- 수정 후 반드시 재검증: 관련 화면 브라우저 확인 + 필요한 빌드/테스트 실행.
- 프론트 빌드/검증 명령은 프로젝트 규칙을 따를 것. [예: frontend에서 npm.cmd run build]

## 카피 점검 기준 (AI 티 제거 포함)
사용자에게 보이는 모든 문구를 점검한다: 제목, 설명, 버튼, 라벨, placeholder, 빈 상태, 오류, 성공, 안내, 툴팁, 필터/검색 요약, 모달, 상태 메시지.

다음 문제를 우선 찾아 개선:
- AI 티가 나는 문구: 과장/홍보성/막연한 표현("완벽하게", "혁신적인", "스마트하게", "매끄럽게" 등), 템플릿처럼 느껴지는 설명, 불필요한 반복.
- 사용자에게 가치 없는 내부 설명: 사용자가 이미 입력했거나 화면에서 바로 보이는 내용을 다시 길게 나열.
- 모호한 문구: 지금 무슨 일이 일어나는지, 다음에 무엇을 해야 하는지 불명확.
- 기계적 나열: 필터/조건/AI 분석 결과를 과도하게 풀어써서 지저분함. 필요하면 요약/접힘/축소/삭제 검토.
- 행동 중심이 아닌 문구: 버튼/안내가 사용자의 다음 행동을 명확히 알려주지 않음.
- 톤 불일치: 같은 기능인데 화면마다 말투/용어/표현이 다름.
- 과도한 안심/면책/설명: 필요한 정보만 남기고 반복 제거.

카피 개선 방향:
- 짧고 구체적으로 쓴다.
- 사용자가 지금 할 행동과 결과를 먼저 보여준다.
- 실제 값(건수, 필터, 상태, 날짜, 선택 항목)을 우선한다.
- 필요한 상세 정보는 기본 접힘/요약으로 숨길 수 있는지 검토한다.
- 기능 의미를 바꾸지 않는다. 애매하면 임의 변경하지 말고 “확인 필요”로 보고한다.

## UI/UX 점검 기준
실제 사용 흐름을 따라가며 아래를 확인:

### 1) 흐름/이해 가능성
- 첫 화면에서 사용자가 무엇을 해야 하는지 명확한가.
- 버튼/탭/필터/모달의 결과가 예측 가능한가.
- 검색/결과/상세/뒤로가기 흐름이 자연스러운가.
- 빈 상태, 0건, 로딩, 오류, 권한 없음 상태에서 다음 행동이 명확한가.

### 2) 시각적 노이즈/정보 밀도
- 불필요하게 큰 설명 영역, 중복 카드/라벨/배지/요약이 있는가.
- 사용자가 자주 안 보거나 방해되는 정보는 접힘/축소/제거 가능한가.
- 중요한 정보와 부가 정보의 우선순위가 명확한가.

### 3) 인터랙션/피드백
- 클릭/제출/필터 적용/초기화/새로고침 후 상태 변화가 보이는가.
- 더블클릭/중복 제출/느린 응답에서 중복 요청이나 UI 잠김이 없는가.
- 포커스 이동, 키보드 접근, 닫기/취소/초기화 후 포커스 복구가 적절한가.

### 4) 레이아웃/반응형
- 데스크톱/모바일에서 가로 overflow, 겹침, 잘림, 깨진 줄바꿈이 없는가.
- 긴 문자열, 이모지, 특수문자, 빈 데이터, 많은 필터 칩에서 레이아웃이 버티는가.
- 깨진 이미지(`naturalWidth===0`)가 없는가.

### 5) 일관성
- 비슷한 화면의 필터/버튼/라벨/정렬/빈 상태 패턴이 일관적인가.
- 화면마다 옵션이 다르면(예: 어떤 화면엔 색상 필터가 있고 다른 화면엔 없음) 실제 데이터/흐름/사용자 가치 기준으로 자연스러운지 판단.
- 코드상 의도처럼 보여도 사용자에게 혼란을 주면 문제 후보로 기록. 단, 제품 의도가 불명확하면 임의 변경하지 말고 “확인 필요”로 분리.

## 필수 확인 항목
- 콘솔 Error / Uncaught Exception / Unhandled Rejection
- 네트워크 4xx/5xx (환경성 401/보조서비스 미기동 등은 제품 버그와 분리 기록)
- 깨진 이미지, 무한 로딩, 잘못된 상태 유지
- 뒤로가기/앞으로가기/새로고침/직접 URL 진입
- 빈값, 초장문, 특수문자, 이모지, 0건, 더블클릭

## 수정 우선순위
1. Critical/Major: 동작 불가, 오류, 데이터 손실 위험, 잘못된 상태/결과, 심한 레이아웃 깨짐.
2. UX 필수: 혼란, 방해, 중복, 불필요한 노출, 이해하기 어려운 문구/흐름.
3. Minor: 문구 다듬기, 간격/정렬/톤 일관성.

## 보고 형식
작업 후 아래 형식으로 보고:

### 1. 점검 범위
- 확인한 URL/라우트
- 뷰포트
- 확인한 주요 플로우
- 실행한 검증 명령
- 미확인 항목과 이유

### 2. 즉시 수정한 항목
각 항목마다:
- `[심각도] Critical/Major/Minor/UX`
- `[위치] URL/화면/컴포넌트`
- `[관찰 근거] 재현 순서 또는 실제 확인 내용`
- `[문제] 사용자에게 어떻게 불필요/혼란/방해/오류였는지`
- `[수정] 무엇을 어떻게 바꿨는지`
- `[파일] 관련 파일 경로`
- `[재검증] 브라우저/빌드/테스트 결과`

### 3. 확인 필요 항목
- 제품 의도가 불명확해 임의 수정하지 않은 항목
- 데이터/백엔드/정책 확인이 필요한 항목
- 큰 구조 개편이 필요한 항목은 `Codex 구조 개편 후보`로 표시

### 4. 최종 상태
- 빌드/테스트 통과 여부
- 남은 리스크
- 사용자 관점에서 남아 있는 주요 아쉬운 점
```

## 빠른 체크리스트

### 카피
- [ ] AI 티 나는 과장/템플릿 문구가 없는가
- [ ] 같은 내용을 반복하지 않는가
- [ ] 버튼/안내가 다음 행동을 명확히 말하는가
- [ ] 오류/빈 상태에서 사용자가 할 일을 알 수 있는가
- [ ] 용어/톤이 화면 간 일관적인가

### UI/UX
- [ ] 첫 화면에서 해야 할 일이 명확한가
- [ ] 불필요한 정보가 기본 노출되지 않는가
- [ ] 로딩/성공/실패/0건 상태 피드백이 명확한가
- [ ] 모바일/데스크톱 레이아웃이 깨지지 않는가
- [ ] 필터/정렬/검색/뒤로가기/새로고침 상태가 자연스러운가
- [ ] 중복 클릭/느린 응답에도 UI가 안정적인가

### 증거
- [ ] 실제 브라우저에서 확인했는가
- [ ] 콘솔/네트워크/레이아웃을 확인했는가
- [ ] 수정 후 같은 흐름을 다시 검증했는가
