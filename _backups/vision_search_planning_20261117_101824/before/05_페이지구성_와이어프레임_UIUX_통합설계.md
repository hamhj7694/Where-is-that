**F2 입력·결과 계약 [AGREED · 2026-11-16]:** 자연어만 / 사진만 / 자연어+사진의 세 입력 모두 이미지 기반 검색과 맥락 기반(설명·조건) 검색을 실행한다. 자연어만 입력해도 **VLM이 공공 습득물의 유효한 실제 사진에서 읽은 맥락·물체·특징을 질의와 비교하여 관련도를 산정**한다. 사진만 입력해도 **VLM이 입력 사진/선택 영역의 종류·색상·형태·눈에 보이는 특징을 해석하여 설명·조건 검색을 자동 수행**한다. 혼합 입력은 자연어와 사진의 특징을 함께 반영한다. 정상 결과 화면에는 **이미지 후보 5건 + 해당 경로 전체 보기 / 설명·조건 후보 5건 + 해당 경로 전체 보기**를 독립적으로 제공한다. 각 5건은 관련 후보가 충분할 때의 목표이며, 실제 후보가 0~4건이면 있는 만큼만 표시한다. 임의 후보로 채우거나 입력 종류만을 이유로 한 경로를 생략하지 않는다.

**필수 범위와 검증 경계:** F2의 VLM 기반 이미지 이해와 세 입력×두 검색 경로는 필수 요구다. 구체 모델·제공자·색인·랭킹·품질·비용·지연·외부 전송 정책은 검증 전이다. 공공 사진 사전 분석/색인/캐시와 후보 재비교를 조합할 수 있으며 매 질의마다 모든 사진을 전수 재분석하도록 고정하지 않는다. 임베딩 단독 실험은 비교 기준선일 뿐 필수 VLM 맥락 처리를 대체하지 않는다. VLM 실패·시간 초과·입력 해석 불확실·동의 미완료는 오류/확인 필요로 표시하고 정상적인 0건이나 입력 미지원으로 위장하지 않는다. 사진 없는 공공 기록은 이미지 경로에서 제외하되 **맥락 경로의 검색 모집단에 유지**한다. VLM 추출 정보는 공식 원문과 별도로 관리하며 동일 물건·소유권·회수를 확정하지 않는다.

### 0.1 변경의 본질과 경계

- **[AGREED: 사용자 목표]** 공개 습득물에 실제 사진이 없는 경우에도 제목·설명·분류·색상·날짜·기관 등의 단서로 검색할 수 있어야 한다.
- **[AGREED: 목표 UX]** F2 검색 결과의 화면은 `이미지 유사 후보(최대 5건)`와 `설명·조건 유사 후보(최대 5건)` **두 섹션**을 제공하고 각각 `전체 보기`로 확장한다.
- **[AGREED: 검색 범위]** 맥락 검색은 **사진 유무와 관계없이 전체 공개 습득물**을 대상으로 한다. **[PROPOSED: 중복 처리]** 첫 화면의 맥락 TOP 5에서는 **이미지 섹션에 이미 표시된 후보만** 중복 제거하고, 뒤의 맥락 후보를 순서대로 보충한다. 맥락 전체 보기의 전체 후보 정책·중복 표시는 G2 실험으로 확정한다.
- **[AGREED]** 이미지 섹션은 **실제로 유효한 물품 사진이 있는 기록만** 대상으로 삼는다. `이미지 준비중` 기본 그림, 404, 깨진 URL을 실제 사진으로 간주하지 않는다.
- **[AGREED: 기능 / OPEN: 구현]** 자연어→공공 사진의 VLM 맥락 비교, 입력 사진→VLM 설명·조건 추출은 필수다. 모델·BM25/임베딩/필터 조합·랭킹·임계값·배포·비용·지연은 PoC 뒤 결정한다. 매 질의마다 모든 이미지를 VLM으로 재분석할 필요는 없으며 사전 분석·색인·캐시·재비교를 검증한다.
- **[AGREED]** 각 결과는 어디까지나 **유사 후보**다. 서로 다른 점수 척도를 `일치 확률`로 합치거나 동일 물건이라고 단정하지 않는다.
- **[AGREED]** F2 결과 페이지는 **지도 중심 화면이 아니며**, 지도는 **개별 후보 상세 하단의 보관기관 보조 영역**에만 노출한다(검증 좌표 확보 시).

## 1. UX 원칙 · 사용자와 맺는 약속

1. **첫 화면은 검색, 인증은 선택:** `/`에서 F1·F2 이용 가능. 헤더 로그인은 별도. F3만 인증 필수.
2. **검색 범위 가시화:** `내가 선택한 사진`(F1) / `경찰 공개 습득물`(F2)을 입력과 결과 주변에 명시.
3. **텍스트만·이미지만·혼합 입력 지원:** F2 사진 없는 사용자는 텍스트만으로 검색. 첨부 이미지는 F2 서버 일시 처리, F1의 원본·인덱스는 기기 로컬.
4. **두 검색 방식의 근거를 분리:** `사진 특징이 비슷한 후보`와 `설명·조건이 유사한 후보`를 서로 다른 UI와 설명으로 노출.
5. **없거나 불확실한 값은 만들지 않음:** 이미지 없는 습득물에 가짜 썸네일 금지; API 누락 필드/가짜 기관·지도핀/확률 수치 금지.
6. **단계별 실패에 복구 행동 제공:** 이미지 검색만 실패해도 맥락 결과는 보여준다. 그 반대도 마찬가지.
7. **행동 전 데이터 경계 명시:** F1→F2는 선택 사진만 명시적으로 전달, F3는 선택 등록 원본과 벡터를 서버에 보관.
8. **모바일 웹의 한계를 안내:** PC 전체 폴더 선택과 모바일 갤러리 전체 자동 색인을 동일하게 보장하지 않음.

## 2. 전체 사이트맵 (IA) 및 페이지 라우팅

> **아래 URL과 페이지 코드는 Figma·개발 커뮤니케이션용 제안안.** 기존 상세기획안과 디자인 가이드의 라우트 표기가 일부 다르므로, **현재 문서의 라우트 이름을 화면 설계 기준으로 사용하되 최종 URL은 PRD에서 결정**한다. 정확한 API 경로는 포함하지 않는다. 아래 전체 보기 라우트의 PROPOSED는 URL 명칭·상세 구현을 뜻하며, 두 경로의 전체 보기 기능·후보 목록·복귀 자체는 필수다.

```text

├─ /gallery                         F1-01~03    로컬 폴더 연결/색인 상태
│  ├─ /gallery/results               F1-04~07    개인 사진 검색/크롭·OCR(조건부)
│  └─ /gallery/photo/:localId        F1-08       원본/세부 보기, F4 연계 CTA
├─ /lost-found                      F2-01~04    습득물 검색 입력/조건/상태
│  ├─ /lost-found/results            F2-05       이미지 TOP 5 + 맥락 TOP 5 요약
│  ├─ /lost-found/results/image      F2-05-I     이미지 검색 전체 보기 [PROPOSED]
│  ├─ /lost-found/results/context    F2-05-C     맥락 검색 전체 보기 [PROPOSED]
│  └─ /lost-found/item/:source/:id   F2-06       습득물 상세 + 하단 보관기관·소형 지도
├─ /valuables                       F3-01~02    인증 게이트/내 물품 목록
│  ├─ /valuables/new                 F3-03~04    물품·사진 등록/저장 확인
│  └─ /valuables/:id                 F3-05~08    상세/편집/삭제/분실 검색
├─ /auth/login                      AUTH-01      별도 로그인(또는 F3 인증 이동)
├─ /settings                        SET-01~03    F1 로컬 인덱스/개인 데이터·계정 설정
└─ /history                         HIS-01      저장 동의 정책 확정 시 조건부 [OPEN]

기능 간 이동:
F1-08 → F4-01~03(사진 선택·동의) → F2-01 / F2-05
F3-05 → 사진/물품 선택 → F2-01 / F2-05 (로그인 확인 및 사용자 명시 선택)
F2-05-I / F2-05-C → F2-06 → 하단 F2-06-MAP 또는 F2-06-LOC-FALLBACK
```

### 2.1 전역 메뉴와 레이아웃

- **헤더:** 로고 `그거어디?`, 옆 짧은 기능 설명(모바일 압축), `홈 / 내 갤러리에서 사진 찾기 / 분실물 찾기 / 소중한 것들 / 설정`, **별도 로그인/계정 버튼**.
- **모바일:** 고정 하단 내비게이션은 **디자인 후보**(이전 가이드상 상단 축약 내비와 비교 후 결정). F2 상세 화면의 외부 링크·스크롤과 충돌하지 않을 것. 로그인 액션을 햄버거 안에 숨겨 유실하지 않을 것.
- **검색 UI:** 홈 중심 채팅형 컴포저(긴 대화 기록 필수 아님), 선택 모드의 범위 라벨, 파일 첨부·조건 수정.
- **공통 정보:** `샘플/DEMO` 라벨, 검색 결과 데이터 출처, 마지막 데이터 확인 시각(확인 가능한 값만), 공식 사이트 연결, 개인정보 안내.

### 4.3 C — F3 등록 및 F2 연결

`소중한 것들 선택 → 비로그인이라면 F3 로그인 게이트 → 로그인 후 원래 단계 복귀 → 물품 사진 1~다수 업로드/촬영 → 원본+사진별 AI 검색용 벡터 저장 안내 → 정보 수정/확인 → 서버 원본·벡터의 연결 성공 검증 → 등록 완료 → 분실 상태/사진 선택 → 명시적 F2 검색 → 두 섹션 결과`.

- 실제 서버에서 **타인 계정의 원본/벡터 접근 차단**. F1의 다른 사진은 F3에 자동 저장 안 함.
- 등록 중 원본 성공·벡터 실패 등 부분 성공은 **완료** 표시 금지. 처리 중/재시도/정리 UX 제공.

### 4.4 D — F4 이미지 연계

`F1 사진 상세 → 검색할 대상 사진/크롭 선택 → F2에서 선택한 사진을 일시 처리한다는 명시적 안내 → 확인 → F2 질의 화면(이미지 미리보기+추가 설명 가능) → 검색 → F2-05 → 임시 질의 원본 처리 종료/삭제 규칙 적용`.

사용자가 취소하면 전송하지 않는다. **경찰 API에 개인 이미지를 자동 제출하지 않음.**

## 6. F2 핵심 — 두 섹션 결과 화면의 상세 명세

### 6.1 정보 구조와 의미 [AGREED / PROPOSED]

**F2-05 화면 목표:** 사용자가 이미지가 있는 후보뿐 아니라 **이미지가 전혀 없는 습득물 기록**까지 검색 후보로 인지하고 검토하도록 한다.

```text
F2 검색 입력·필터·질의 요약
  ├─ 섹션 A: 실제 습득물 사진 비교가 가능한 후보 [이미지 TOP 최대 5]
  │     → 각 후보 클릭 = 동일한 F2 상세 페이지
  │     → [이미지 검색 전체 보기] = F2-05-I
  └─ 섹션 B: 사진 유무와 무관한 기록의 제목·설명·조건 관련 후보 [맥락 TOP 최대 5]
        → 이미지 섹션에 표시된 후보는 요약 화면에서 제외(제안)
        → 사진 없으면 '등록된 사진 없음' + 텍스트 정보로 카드 구성
        → [맥락 검색 전체 보기] = F2-05-C
```

### 6.4-A 세 입력의 필수 VLM 해석 계약 [AGREED / 구현·성능 미검증]

| 입력 | 이미지 기반 검색 — 사진 특징 후보 | 맥락 기반 검색 — 설명·조건 후보 |
|---|---|---|
| 자연어만 | 공공 실사진의 VLM 맥락·물체·특징과 자연어 설명의 관련도를 비교한다. 사용자 사진 첨부를 요구하지 않는다. | 자연어를 공개 기록의 물품명·설명·분류·색상·조건과 비교한다. |
| 사진만 | 입력 사진/선택 영역과 공공 실사진의 시각 특징·VLM 맥락을 비교한다. | 입력 사진을 VLM으로 해석해 검색용 설명·조건을 자동 구성하고 사진 유무 무관한 공개 기록을 검색한다. 자연어 추가 입력을 요구하지 않는다. |
| 자연어+사진 | 입력 문장과 사진 특징을 함께 반영해 공공 실사진 후보의 관련도를 판단한다. | 자연어와 VLM이 읽은 입력 사진의 설명·조건을 함께 반영한다. 사용자 입력과 AI 추정의 충돌은 표시·수정 가능하게 한다. |

사용자는 텍스트만 쓰거나 사진만 넣어도 두 검색을 시작한다. 사진에서 추정한 검색 특징은 확인·수정·빼기를 제공하되, 매번 설명을 직접 작성/확정해야만 검색되는 필수 관문으로 만들지 않는다. 인식이 실제 실패했거나 설명과 사진이 충돌하면 재시도·수정·선택적 입력 보완을 제공한다.

```text
자연어만 → 공공 사진의 VLM 맥락과 문장 비교 + 실제 기록의 설명·조건 검색
사진만 → 입력 사진 VLM 해석 → 이미지 관련도 검색 + 자동 설명·조건 검색
혼합 → 명시 문장 + VLM 사진 특징 → 두 경로 검색
모든 정상 입력 → 사진 특징 후보 최대 5 + 전체 보기 / 설명·조건 후보 최대 5 + 전체 보기
```

VLM 기능은 필수이며 모델·공급자·배포·성능·비용은 검증 전이다. 공공 사진의 해석 정보와 공식 원문은 분리한다. 입력 사진/추출 특징은 일시 처리하며, 외부 VLM 전송에 필요한 고지·동의·보존 정책을 충족하기 전에는 자동 전송하지 않는다. 불확실한 브랜드·소유관계·기관·주소를 만들어 공식 사실로 쓰지 않는다.

### 6.5 중복·정렬·결과 개수 정책 [PROPOSED]

1. **검색 자체는 전체 모집단 대상**으로 각각 수행한다. 맥락 경로에서 처음부터 `사진 있는 기록`을 삭제하지 않는다.
2. 요약 화면에서 `이미지 A에 실제 노출된 item_key`를 제외한 **맥락 다음 순위 후보**로 TOP 5를 채운다. `item_key`는 API별 안정적인 키를 사용하고 출처 간 실제 중복/재게시 여부는 별도 정책으로 처리.
3. 이미지 A 결과가 2건뿐이면 맥락 B는 A의 **실제 노출 2건**만 제외; 맥락 5건을 위해 관련성이 낮은 후보를 억지로 끌어오지 않는다.
4. 전체 보기의 기본 제안은 **독립 검색 결과를 섹션별 순위로 보여주되**, 이미 다른 섹션에 보였던 동일 기록에는 `이미지 검색에서도 표시됨` 같은 중복 표시를 고려한다. 완전 제거/접기/중복 허용은 실사용자 테스트로 결정.
5. 1차 결과에서의 `TOP 5`는 **최대치**다. 미리 정한 품질 기준 미달이면 적게 표시하고 상태 안내. 적정 임계값은 검증 전 `[OPEN]`.
6. 수십~수만 기록이 있는 경우 전체 보기는 **서버 페이지네이션 또는 커서 기반**으로 제공하는 방향을 검토. 결과 개수·마지막 동기화 시점은 실제 수치만 표시.
7. 필터·검색어를 바꾸면 **두 섹션을 함께 재검색**하되 섹션별 독립 로딩/오류를 유지. 무관한 앞선 이미지 검색 결과를 새 질의로 가장하지 않는다.
8. 이미지 URL이 유효했다가 끊어지면 `이미지 있음`을 재검증하고 해당 기록의 **맥락 검색 자격은 유지**한다. 텍스트만 보고 실제 사진을 만들지 않는다.

### 6.6 카드 세부 요소 · 인터랙션

**이미지 카드 `FoundImageResultCard`:** 실제 물품 사진 / 물품명 / 출처·습득일(확인된 값만) / 선택시 상세 / `사진이 유사한 후보` 설명. 이미지는 object-fit cover만 고집하지 말고 지갑·핸드폰 전체가 잘리지 않도록 thumbnail fit 검토. `이미지 로딩 오류`면 무한 스켈레톤 대신 오류 상태로 전환하고 재검색 시 서버 판정과 동기화.

**맥락 카드 `FoundContextResultCard`:** `NoPhotoThumbnail`(등록 사진 없음인 경우) 또는 실제 이미지 / 제목과 핵심 조건 / `관련 단서: 물품명·색상`처럼 **실제 존재하는 매칭 근거만** / 습득일·공식기관(있을 때) / 상세 / 비슷한 종류의 다른 실물일 수 있다는 안내. `설명 없음`은 결핍을 숨기지 않고 비교 가능한 필드만 보여준다.

**상태 라벨:** `사진 있음/등록된 사진 없음`은 API 미리보기의 존재만으로 결정하지 않는다. 유효한 실제 물품 사진인지 서버에서 검증된 경우에만 `사진 있음`; 기본 이미지/썸네일 무효/정보 없음은 분리할 수 있도록 설계.

**터치/접근성:** 카드 전체 클릭 + 명확한 상세 CTA, 읽을 수 있는 대체텍스트(존재하는 출처정보만), 키보드 탭 순서, 좌우 스크롤 힌트, 초점·에러/부분 결과 안내 ARIA. 다른 종류의 후보라는 사실을 색상만으로 구분하지 않음.

**진입·복귀 규칙:** `전체 보기`는 항상 선택한 검색 경로의 후보만 펼친다. 필터·검색어·스크롤/선택 결과는 가능한 범위에서 복귀 시 복원하되, API 데이터 갱신으로 레코드가 달라졌을 때 과거 후보가 보존되는 것처럼 약속하지 않는다. 새 탭/뒤로가기/직접 URL 진입도 오류 없이 처리한다.

### 7.1 사진 없는 기록의 정보 부족 상태

- 제목만 존재하면 **제목+출처+습득일(존재 시)** 수준으로 보여 주고, 설명·색상·보관기관을 임의 생성하지 않는다.
- 사진 없는 결과의 개수를 실제 API 표본으로 확인하기 전 `사진 없는 물건도 모두 찾아줍니다` 같은 보장 카피 금지.
- 이미지 없는 기록은 이미지 섹션에 **절대 카드로 끼워 넣지 않음**. 맥락 섹션에 나오게 하되, 검색 근거가 빈약하면 관련도 기준으로 내려갈 수 있다.
- 데이터 자체의 사진 보유율·제목/설명 채움률·카테고리/색상 누락률을 `EXP-06`에서 측정하고, 별도 이미지/맥락 모델의 검색 효용을 `EXP-05`와 결합해 평가.

## 8. F2 개별 상세 + 하단 보관기관 소형 지도

### WF-08: 상세 페이지 (데스크톱·모바일 모두 위계 동일)

```text
┌────────────────────────────────────────────────────────────────────┐
│ [← 검색 결과]                                      [공식 상세 확인]│
│                                                                    │
│   [물품 사진 / 등록 사진 없음]   물품명 · 유사 후보 안내            │
│                                 분류/색상(원문에 있을 때)          │
│                                 습득일·관리번호·출처              │
│                                 습득 장소(있는 경우)              │
│                                 접수 기관(있는 경우)              │
│                                                                    │
│ 물품 설명/특징 (공공 API 원문, 없는 항목 추정 금지)                │
│ ※ 동일 실물인지 확정할 수 없으며 공식 기록으로 확인해야 함        │
│ ────────────────────────────────────────────────────────────────   │
│ 보관기관 및 위치                 ← 상세 페이지 하단 보조 섹션     │
│ [기관명] [공식 확인 주소] [전화] [정보 확인일]                     │
│ ┌────────────────────────────────────────────┐                     │
│ │ 검증된 보관기관 주소의 소형 지도: 1개 마커 │ (verified만)        │
│ └────────────────────────────────────────────┘                     │
│ [지도에서 보기] [외부 길찾기] [전화] [공식 상세 확인]              │
│ 방문 전 해당 물건의 보관 여부를 기관에 확인하세요.                │
└────────────────────────────────────────────────────────────────────┘

주소/좌표/기관 정보가 미확인·다의적이면 지도 블록 자체를 렌더링하지 않음.
대신 확인된 정보와 공식 링크/문의 CTA만 표시.
```

**주소·좌표 판정:** `verified`일 때만 지도·마커. `address_only`, `ambiguous`, `missing`, `invalid`, `provider_error`이면 지도 숨김. API 원문의 `습득 장소`/`접수 장소`를 **현재 보관기관 주소로 사용 금지**. 기관의 실시간 물건 위치 GPS가 아니다.

**상세 접근:** 이미지 TOP/맥락 TOP/전체 보기 모두 같은 상세 페이지를 열며, 원래 검색 결과 경로로 돌아갈 수 있도록 복귀 맥락 유지. 출처/마지막 확인 시간/불확실성 고지 표시. 특정 물건에 등록 사진이 없는 경우에도 상세 페이지 자체는 이용 가능해야 한다.

## 13. 제안 API/UI 데이터 계약 (아직 구현·검증 전)

> 아래는 **UX가 필요로 하는 최소 데이터 필드의 예시**. 실제 API-01/02와 FastAPI 엔드포인트의 확정 계약이 아니다. **공공 원문 필드는 확인된 API 응답에 매핑하고, VLM 파생 필드는 별도 출처·모델·버전·처리 상태로 관리한다.**

```ts
// 제안 타입. API 필드 이름·유효성은 G0 실호출 후 확정.
type SearchMode = "gallery" | "lost-found";
type ResultChannel = "image" | "context";
type SectionStatus = "idle" | "loading" | "success" | "empty" | "error" | "needs_confirmation";
type InputType = "text" | "image" | "mixed";
type VisualFeature = { text: string; source: "query_image_vlm" | "public_image_vlm"; uncertain: boolean };

type FoundItemCandidate = {
  key: string;               // source + stable item id, 계약 검증 후
  source: string;            // 경찰관서/포털기관 등
  title?: string;
  description?: string | null;
  category?: string | null;
  color?: string | null;
  foundAt?: string | null;
  foundPlace?: string | null;
  custodyName?: string | null;   // 공식 확인된 정보만
  officialUrl?: string | null;
  photoStatus: "verified_photo" | "no_photo" | "invalid" | "unknown";
  photoUrl?: string | null;      // 공공 이미지 사용권·접근성 검토 후
  matchedFields?: string[];     // 실제 존재하고 검색된 필드만
  recordUpdatedAt?: string | null;
  derivedVisualDescription?: string | null; // VLM 파생 설명, 공식 description 덮어쓰기 금지
  visualAnalysis?: { status: "pending" | "success" | "failed"; modelId: string; promptVersion: string; imageVersion: string; processedAt?: string };
};

type SearchSection = {
  channel: ResultChannel;
  status: SectionStatus;
  items: FoundItemCandidate[];  // 요약 화면에서는 최대 5
  hasMore?: boolean;
  nextCursor?: string | null;   // 전체 보기 계약 확정 전
  message?: string | null;
  errorCode?: "vlm_error" | "timeout" | "interpretation_uncertain" | "consent_required" | "source_error";
};

type LostFoundSearchView = {
  requestId: string;
  inputType: InputType;
  queryFeatures?: VisualFeature[]; // 요청 범위 임시 데이터
  querySummary: string;
  filterSummary: string[];
  dataCheckedAt?: string | null;
  sections: { image: SearchSection; context: SearchSection };
  isDemo: boolean;
};
```

**공공 데이터 수집 방향:** API-01/02 각각에서 `원문 물품명·분류·색상·설명·일시·기관/장소·이미지`를 확보 가능한 만큼 보관하고, **이미지 유효성**과 **텍스트·메타데이터 유효성**을 **별도 품질 지표**로 추적한다. 실제 사진에 대해서만 이미지 임베딩을 만들며, 사진 없는 기록도 제목/조건 인덱스를 통해 검색 가능해야 한다. 신규·수정·반환·삭제 변경을 주기 점검하는 서버 동기화는 G0에서 주기·가능 여부를 검증한다. 검증 전 6시간 같은 특정 주기를 확정하지 않는다.

**개인 사진 경계:** F2 질의 첨부 사진은 사용자 선택 후 자체 서버 검색에 일시 처리하는 범위를 명시. 외부 VLM 전송은 별도 동의·약관·보존정책 확인 전 사용을 확정하지 않음. 조회용 개인 원본을 경찰 API로 자동 제출하지 않는다.

- [ ] 공공 원문과 VLM 파생 특징의 출처를 구분하고, 모델/프롬프트 버전·처리 시각·이미지 버전·상태를 추적한다.

### 15.1 디자인 수용 체크리스트

- [ ] 브랜드명 `그거어디?`와 설명 `내 사진 · 내 물건 찾기`를 사용하고 GPS 추적 오인을 줄인다.

- [ ] F2 결과는 **이미지 TOP 최대 5 + 전체 보기 / 맥락 TOP 최대 5 + 전체 보기**를 명확히 구별한다.
- [ ] **사진 없는 습득물**도 맥락 후보 카드·상세에 표시될 수 있다.
- [ ] 맥락 검색이 **사진 있는 기록을 자동 제외하지 않으며**, 요약 중복 처리만 따로 적용한다.
- [ ] 이미지/맥락 두 섹션의 빈·오류·부분 성공 상태가 독립적으로 동작한다.
- [ ] 모든 카드에 공식 출처로 가는 경로가 있고 불확실성 고지가 있다(출처가 실제 있는 경우).
- [ ] 맥락 결과에 근거 없는 제목·설명·사진 또는 `동일물건 확률`을 만들지 않는다.
- [ ] F2 전체 보기는 해당 채널로만 이동하고, 다시 요약으로 돌아갈 수 있다.
- [ ] F2 상세 하단의 **보관기관 및 위치** 영역에서 verified 시에만 소형 지도 1개를 표시한다.
- [ ] F1 사진은 로컬, F3 등록 원본+사진별 벡터는 계정 서버, F4는 선택 후 일시 전달로 정확히 구분한다.
- [ ] 360/390/768/1440px에서 제목·카드·필터·전체 보기·지도 안내가 잘리거나 숨지 않는다.
- [ ] Figma 프레임별 `frame_id/route/goal/FR-ID/state/data_contract/demo_status`가 남는다.

### 15.2 최신 카피 적용

사용자용 문장은 `06_UI_최신_카피.md`가 기준이다. 기본 입력 안내는 “글만 적거나 사진만 추가해도 검색할 수 있어요. 함께 입력해도 좋아요.”다. 정상 상태에서 설명 추가/사진 첨부를 다른 검색 경로의 필수 조건으로 안내하지 않는다. “사진에서 검색 특징을 읽지 못했어요.”는 실제 VLM 해석 실패에만 쓴다. 결과 링크는 “사진 특징 후보 전체 보기 / 설명·조건 후보 전체 보기”로 통일한다.
