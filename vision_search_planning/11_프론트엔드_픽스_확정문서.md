## 0. 문서 운영 규칙

### 0.1 우선순위

1. 사용자의 최신 직접 지시
2. **이 문서(11번 픽스 확정문서)** — 현재 프론트엔드의 확정 상태
3. `10_디자인_마스터_작업로그.md` — 사용자 작업 근거(삭제·수정 금지, 새 변경은 로그에 추가)
4. 루트 `AGENTS.md`, `frontend/AGENTS.md`, `agents/*.md` — 에이전트 운영 규칙
5. 파일명에 `_old`가 붙은 문서 — **읽기 금지·참조 금지·우선순위 없음**

새로운 사용자 변경이 확정되면 기존 항목을 지우지 말고 **이 문서와 10번 로그에 새 항목을 추가**한다. 충돌하면 최신 사용자 지시가 이전 확정을 대체하며, 대체 관계를 반드시 기록한다.

### 0.2 `_old` 문서 읽기 금지 (강제)

- 파일명에 `_old`가 들어간 `.md` 파일은 **AI 에이전트가 열지 않는다**. 내용 인용·요약· 비교·"참고한다"도 금지한다.
- 과거 기획/와이어프레임/카피/Figma 가이드는 전부 `_old`로 보관되었으므로 디자인 근거로 사용하지 않는다.
- 과거 상태를 알아야 하는 드문 경우에는 사용자에게 명시적으로 확인받은 뒤 `_backups/` 원본을 별도로 다룬다. `_old` 파일을 자동으로 읽어 현재 디자인을 추론하지 않는다.
- `_old` 파일은 **수정하지 않는다**. 이름을 되돌리거나 내용을 갱신하지 않는다.

### 1.1 연결 선행·인페이지 연결 [DML-001/004/005/006/019/040]

- 미연결 상태에서는 **검색 입력창을 표시하지 않는다**. 먼저 `/gallery` 안에서 갤러리·폴더 연결을 표시한다. 연결 팝업을 되살리지 않는다.
- 미연결 안내 문구는 **“찾고 싶은 사진이 있는 갤러리나 폴더를 연결해 주세요.”** 다. 직접 진입·새로고침 결과는 샘플 사진이 아니라 연결 안내다.
- 최신 DML-103: 이전에 연결해 둔 갤러리가 브라우저에 저장되어 있으면 새로고침·재진입 시 연결 상태로 복원된다. 위 연결 안내는 저장된 연결이 없거나 해제한 경우에 적용된다.
- `샘플 갤러리 보기`는 삭제 상태다. `화면 체험` 진입 버튼은 일반 UI에서 숨긴다.
- 선택한 폴더의 **모든 하위 폴더 이미지**를 모은다. 미리보기 장수가 모집단을 제한하지 않는다. 같은 파일명이라도 상대경로가 다르면 각각 유지한다.
- Windows 개발용 사진·폴더 선택기는 브라우저의 앞쪽 창을 소유자로 지정해 창 뒤에 가려지지 않는 모달로 연다(DML-066).
- 최초 연결/이미지 추가 창의 **‘전체 경로도 함께 연결하기(선택)’** 기준 경로 입력 유지. `GalleryBasePathField`는 5줄짜리 최소 구현을 그대로 둔다.
- 검색 방식 선택 바는 정확히 `/`, `/gallery`, `/lost-found`에서만 표시한다(`App.tsx`의 `isInputPage`). 결과·전체목록·상세·기록·설정에는 공백도 남기지 않는다.

### 1.2 미리보기·추가·더보기 [DML-003/007/008/011/015/018/020/021]

`GalleryPreview.tsx`의 현재 상수를 그대로 유지한다.

- `DESKTOP_PREVIEW_LIMIT = 6`, `MOBILE_PREVIEW_LIMIT = 4`.
- **PC**: 6장 이하 → 사진 전부 + `이미지 추가` / 7장 이상 → **사진 6장 + `이미지 더보기`만**. `이미지 추가` 숨김. (DML-011의 7장 기준, DML-015의 ‘7장 이하 전부’는 DML-018이 최종 대체)
- **모바일**: 56×56px, 간격 4px, 최대 4장. 5~6장이면 4장+더보기 아래 44px `이미지 추가` 줄을 함께 제공. 7장 이상은 4장+더보기만.
- 썸네일은 PC 112px, 클릭·키보드로 `PhotoViewer` 확대, 닫기/Esc 후 해당 버튼으로 포커스 복귀.
- `이미지 더보기`는 `/gallery/results?view=all`의 **실제 연결 이미지 전체목록**이다. 검색/기록을 만들지 않고 샘플로 대체하지 않는다.
- 전체목록(`GalleryResults`의 `browse`) 도구영역 왼쪽 끝에 `이미지 추가`(gallery-toolbar__add), 오른쪽에 정렬을 유지한다. 과거 검색 결과(`찾은 이미지`)에는 이 버튼을 넣지 않는다.
- 새 연결은 선택 안 중복 제거, 추가는 현재 연결+선택 안 중복 제거. 기준은 **파일 내용 SHA-256**, 이름·경로·시간이 아니다. 동명·다른 내용은 유지한다. 검사 중 안내/취소, 읽기 실패 시 기존 연결·입력·기록 보존, 취소된 처리 commit 금지. 누적 중복 선제 정리는 하지 않는다.
- `GalleryConnection`의 복귀 버튼 카피는 **`← 돌아가기`** 다(DML-017). 연결 유지 + 브라우저 직전 경로 `navigate(-1)` 복귀, 해제·검색·기록 변경 없음.

### 1.3 참고 사진·크롭 [DML-009/010/013/023/032]

- 갤러리 설명은 **“연결한 갤러리에서 사진이나 스크린샷을 찾을 수 있어요.”** 다(`copy.ts`).
- 참고 사진은 **한 장**. 큰 미리보기 + 같은 창 안 사각형 영역 선택 + 키보드 정밀 조정 + `전체 사진으로` + 최종 `이 사진 사용`에서만 확정.
- `SearchComposer`의 64×64px 첨부 미리보기(type=button, X 제거 버튼과 분리) 클릭/Enter로 기존 참고 사진 창 재열기. 사진 클릭은 검색을 제출하지 않는다.
- 원본 관계는 `reference-photo-model.ts`의 File 세션 메모리(WeakMap)에만 보존. 페이지 해제·새로고침 후 유지되지 않는다.
- 파일 입력 창의 `cancel`은 부모 창을 닫지 않는다(`Modal.tsx` 공통). 창 X/취소/Esc 후 임시 사진·원본·크롭 사각형·선택을 복원하고, 최종 사용 전에는 검색 첨부를 바꾸지 않는다.

### 3.1 로그인 계정의 기록 영속 [DML-061/064]

- 위 데이터 경계 중 **“새로고침하면 사라진다, 서버에 검색 내용을 저장하지 않는다”** 는 항목은 **로그인하지 않은 상태에 한해 유효**하다. 로그인 상태에서는 ‘찾은 기록’이 계정에 저장되고 다시 로그인해도 이어진다(DML-061이 부분 대체).
- 로그인 전에 만든 로컬 기록은 최초 로그인 시 계정으로 이관된다. `id`가 같은 기록은 합치고, 손대지 않은 데모 시드는 이관하지 않는다.
- 로그아웃 시에는 로컬 상태만 초기화되고 계정에 저장된 기록은 남는다(DML-064). 화면의 두 영역·이동 버튼·삭제 확인 문구·표시는 바꾸지 않는다.

## 4. 사진 등록해 두기 (F3) — 픽스

기준 코드: `features/workspace/ValuablesPages.tsx`, `data.ts`, `features/search/LostReferenceDialog.tsx`(variant="valuable"), `TransferDialog`, `CropDialog.tsx`, `styles/pages.css`.

### 4.1 이름·목록 [DML-041/045/046]

- 사용자에게 보이는 용어는 **`사진 등록해 두기`**. `소중한 것들`로 되돌리지 않는다. 로그인·계정·설정의 같은 기능 표도 이 용어로 정렬.
- 목록 제목 **`소중한 물건 사진 보관함`**, 설명 **`소중한 물건을 잃어버리기 전에 사진을 미리 등록해 보세요!`** 고정.
- 기본 정렬은 등록 시각 `createdAt` 최신순(없으면 `updatedAt` 대체). 검색어가 등록 정보에 그대로 포함되면 `키워드 검색`, 그렇지 않으면 단어 조합 기반 `자연어 검색 · 현재는 등록한 정보의 단어를 기준으로 찾아요.` 표시. AI 검색 완료로 표현하지 않는다.
- 정렬 옵션: 최신 등록순/최신 수정순/최신 조회순/제목순. 상세를 연 시각 `viewedAt`을 조회순에 사용. 카드 설명에 `등록 날짜 · …`.
- 그리드: 데스크톱 **1행 5개, 간격 20px**, 태블릿 2개, 모바일 1개. 검색 결과 없음과 미등록은 별도 안내.

### 4.2 사진 등록·수정·상세 [DML-042/047/048/050/051/053]

- `샘플 사진 사용` 버튼은 제거 상태다. `사진 추가`는 F2 참고 사진 모달 흐름(`variant="valuable"`)을 재사용하며 최대 6장, `사진 추가 (현재 장수/6)`.
- F3 모달에는 F2 전용 **사진 준비 팁·방향 그림 안내를 넣지 않는다**. 단, **사진별 기본 방향 선택 창은 노출**한다(DML-050이 DML-042의 비노출 결정을 대체). 선택지와 기본값은 F2와 동일, 선택 사항.
- 방향·사진 변경은 임시 편집이며 최종 `사진 n장 사용`에서만 폼 반영. 취소·닫기는 기존 사진·방향 보존. 방향은 재수정 시 보존, F2 전달 시 함께 전달. 자동 판별 아님.
- `이 사진 삭제`와 수정 화면의 사진 설명 옆 `X`는 즉시 제외하지 않는다. **`삭제`를 정확히 입력 + 별도 삭제 버튼** 필요(DML-053). 취소 시 사진·방향 보존, 원본은 기기에 유지. F2 모달 삭제 동작은 변경하지 않는다.
- 수정 화면 사진 배치는 상세와 동일: **선택한 큰 사진 위 + 가로 썸네일 아래**. 선택·삭제·추가·모바일 가로 스크롤 유지.
- 상세 정보 영역에 **생성 시간/최신 수정 시간/최신 조회 시간**을 날짜+시각으로. 조회 기록 없음은 `아직 조회 기록이 없어요`.
- 상세·수정의 큰 사진에 현재 사진의 방향 라벨, 썸네일에 각 사진 방향 라벨. 확인 불가하면 `미지정`(DML-051).
- 등록/삭제 확인 창에서도 **`삭제` 입력** 필요(DML-052). 임시 항목·서버 미저장 고지를 유지.

### 4.3 F3 → F2 전달 [DML-049]

- 상세의 `이 사진으로 분실물 찾기` 창에서 등록 사진 **최대 6장 선택·해제**. 최초 선택은 현재 보고 있던 사진.
- 명시적 확인 전에는 F2 입력을 바꾸지 않는다. 확인 시 선택 묶음만 F2 참고 사진으로 전달하고 `/lost-found`로 이동.
- F1 개별 이미지 상세의 전달은 **한 장** 유지.

### 4.4 계정 저장·프로필·탈퇴 [DML-061/062/063/064/065]

- 로그인 상태의 등록 물건은 계정에 저장되고 새로고침·재로그인 후에도 유지된다. 등록 사진은 data URL로 계정 콘텐츠에 보관한다. **미등록 임시 상태와 갤러리 원본은 계속 브라우저에만 있다.**
- `/account`에서 프로필 이미지(8MB 이하)·닉네임을 수정 저장하고, 회원가입일·최신 방문일을 확인한다. 카카오 재로그인은 사용자가 바꾼 프로필을 덮어쓰지 않는다.
- 프로필 편집은 이미지 미리보기·선택 영역과 닉네임·저장 영역을 분리해 배치한다. 모바일에서는 한 열로 정돈하며, 이미지 용량 제한·저장·제거 동작은 유지한다(DML-065).
- 탈퇴는 **‘계정을 탈퇴합니다’** 정확 입력 + 별도 확인 창이 필요하다. 탈퇴 시 계정·기록·등록 사진·세션이 삭제되고 기기 원본은 남는다.
- 목록·등록·수정·상세의 레이아웃·카피·크기·상태 전환·포커스는 그대로다. “임시 항목” 문구는 로그인 여부에 따라 저장 상태를 정확히 설명하는 범위에서만 조정한다.

## 6. 코드 변경 시 AI가 지켜야 하는 체크리스트

1. 위 4개 영역의 파일을 **열어서 현상만 확인**하고, 수정 요청이 없으면 아무 것도 바꾸지 않는다.
2. 색상·글꼴·간격·버튼 크기(44px/48px), 문구, 순서, 표시 기준값(6/7/8장, 4장, 56/64/72/96/112px)을 임의로 바꾸지 않는다.
3. DML의 “대체” 관계를 되돌리지 않는다. 특히:
   - PC 미리보기 = DML-018(6장+더보기) / 모바일 56px·4장
   - 도우미 반영 = DML-033(재검색 시 일괄) / 재검색 기록 = DML-038(같은 ID)
   - F3 방향 = DML-050(방향 선택 창 노출) / 방향 안내 = DML-034(팁 안쪽)
   - 파일 위치 = DML-040(경로 없어도 버튼 활성)
4. 실제 AI/API/서버/영속 저장/인증 기능을 추가하거나 “연결됨”으로 표현하지 않는다. 기존 미연결 고지를 지우지 않는다. **단, 로그인·계정 인증 한정으로 DML-054→055/056(8장)이 이 항목을 대체한다.** AI/VLM·검색 API·경찰청 API·서버 원본/벡터 저장·영속 사진 저장은 여전히 미연결이며 “연결됨”으로 표현하지 않는다.
5. `frontend/artifacts/**`는 사용자 검수 증거다. 삭제·덮어쓰기·재사용하지 않는다.
6. 변경이 불가피하면 **사용자 명시 지시**를 받은 뒤 10번 로그에 새 DML을 추가하고, 이 문서의 해당 항목을 “대체됨”으로 표시한다. 기존 항목을 삭제하지 않는다.
7. `_old`가 붙은 파일은 읽지 않는다. 파일 목록에서만 존재를 확인하고 참조하지 않는다.
8. 4항의 예외는 **로그인·계정 인증(DML-054→055/056)** 에서 **계정 소유 기록·사진 저장, 프로필 수정, 계정 탈퇴(DML-061~063)** 로 확장됐다. AI/VLM·검색 API·경찰청 API·서버 원본/벡터 저장은 여전히 미연결이며 “연결됨”으로 표현하지 않는다.
9. 로그아웃은 `signOut()`만 호출하고 `user === null` 전환 이펙트가 상태를 초기화한다(DML-064). `onLogout`에서 항목을 직접 초기화해 계정 콘텐츠를 덮어쓰지 않는다.
10. 계정 저장 구현으로 인한 고지 문구 변경은 **저장 위치에 대한 사실 정정에 한정**한다. 확정 4개 영역의 레이아웃·카피·크기·상태 전환·포커스·데이터 경계는 임의로 바꾸지 않는다.
11. **DML-069 [FRONTEND]가 2.2항의 샘플 결과 고지를 대체한다.** 검색 결과·더보기·상세보기는 경찰청 공개 API 실데이터를 API 순서 그대로 표시한다. AI 유사도 검색은 없으므로 점수·재정렬·`matchReasons`는 만들지 않는다. 키는 브라우저에 두지 않고 서버 프록시만 호출한다. 데모(`source=demo`) 상세 미리보기 상태는 유지한다. 기존 항목을 삭제하지 않는다.
12. **DML-070 [FRONTEND] 표시 중복 제거·페이지 이어받기.** 물품명·색상·분류·습득일·보관기관이 같은 후보는 화면에 1건만 표시한다(백엔드 ID 중복 제거와 별개). `다음` 누르면 API 다음 페이지를 이어 받아 결과와 페이지 수가 늘어난다. 12장 단위·더보기·초점·레이아웃 규칙은 그대로다.
13. **DML-071 [FRONTEND] 검색 조건 아코디언.** `[검색 조건]` 모달 대신 열리고 닫히는 인라인 아코디언을 사용한다. 입력 높이 36px의 낮고 넓은 필터 2행 배치, 시작일 `(이 날짜부터)`·종료일 `(이 날짜까지)` 괄호 설명을 추가한다. 열기·닫기 초점 이동은 접근성 규칙을 유지한다.
14. **DML-072 [FRONTEND] API 기준 필터 옵션.** 물품 분류는 경찰청 검색 응답 `prdtClNm`의 대분류·소분류 옵션을 사용하고, 색상 필터는 제거한다(자연어 검색 대상). `습득지역`은 **`분실 예상 지역`**으로 바꾸고 17개 시도 옵션을 제공한다. API에 지역 코드가 없어 보관기관 위치에서 유추하며 그 사실을 도우미 문구에 밝힌다. 분실 지하철 호선은 API 데이터가 없어 **추가하지 않는다**(사용자 확인 완료). 기존 항목은 삭제하지 않는다.
15. **DML-073 [FRONTEND] 필터 배치.** 사물 방향은 분실 예상 지역 오른쪽에 둔다. 1행 분류·지역·방향, 2행 시작일·종료일. 필터 높이·초점·레이아웃 규칙은 그대로다.
16. **DML-074 [BACKEND] 지도·길찾기 서버 API.** 카카오 **JS 키만** 브라우저에 전달한다(사용자 승인). REST 키와 경찰청 서비스키는 서버 전용이다. 상세에 카카오 Local 장소 정보(이름·전화·주소·분류·placeUrl)를 추가하고, 영업시간은 API 미제공으로 표시한다. `POST /api/lostfound/route`로 거리·예상 시간·경로·길안내 링크를 계산한다.
17. **DML-075 [FRONTEND] 상세 지도 패널.** 상세 하단에 실제 카카오 지도와 보관 장소 마커를 표시한다. 장소 정보·거리·예상 시간·길안내 링크를 함께 보여 주고, `현재 위치에서 출발` 버튼으로 GPS를 출발지로 설정한다. 기본 출발지는 서울시청이며 거리 계산은 지도 SDK 실패와 무관하게 동작한다. 기존 항목은 삭제하지 않는다.
18. **DML-079 [FRONTEND] 출발지 영역 리디자인.** 출발·도착은 한 줄 경로 칩으로 표시하고, GPS 버튼은 입력 라벨 오른쪽에 둔다. 입력창과 `출발지 설정`은 한 줄로 고정하고, 거리·시간은 강조 배지로, 하단 버튼은 `카카오맵 길안내`를 넓게 하고 `장소 정보 보기`를 우측에 배치한다. 출발지 입력·GPS 동작과 접근성 규칙은 그대로다. DML-075의 기본 출발지 문구는 DML-078이, 이 배치는 DML-079가 대체한다.
19. **DML-080 [BACKEND] 전체 목록 API.** `POST /api/lostfound/list`는 검색어 없이 경찰청 두 소스의 공개 목록을 페이지 단위로 가져온다. 기존 검색 API의 검색어 필수 규칙과 부분 실패 비캐시 규칙은 유지한다.
20. **DML-081 [FRONTEND] 직접 찾기 화면.** 헤더의 `내 사진 · 내 물건 찾기` 우측에 `직접 찾기` 버튼을 두고 `/direct-search`를 연다. 이 화면은 AI 검색을 쓰지 않고 공개 API 목록을 그대로 표시하며, 키워드 검색과 기존 검색 조건 아코디언을 사용할 수 있다. 우측의 `검색 도우미 AI`는 펼치고 접을 수 있는 안내 패널이며 검색에 적용되지 않는다. 기존 항목은 삭제하지 않는다.
21. **DML-086 [FRONTEND] 상세 보관정보·조회번호 표시와 안내 문구 정정.** 상세에 보관상태·보관구분·관리번호·습득순번·기관번호를 표시하고, `보관기관 및 위치` 안내를 `실제 보관 여부는 연락처로 문의 부탁드립니다.`로 고정한다. 공개 API에 별도 민원번호가 없으므로 `atcId`+`fdSn`과 `orgId`를 조회 식별자로 쓴다. 검색 순서·점수·카드 항목은 바꾸지 않는다.
22. **DML-087 [FRONTEND] 상세 표시 항목 정리.** DML-086의 보관구분·습득순번·기관번호 표시를 빼고, `습득일` 뒤에 `습득 시간`(`fdHor`)을 추가한다. 관리번호(`atcId`)와 안내 문구 정정은 유지한다. `fdSn`은 URL 라우팅용으로만 남긴다. 검색 순서·점수·카드 항목은 바꾸지 않는다.
23. **DML-088 [FRONTEND] 상세 `유사 후보` 배지 제거.** 상세 상단의 상태 배지를 데모·실제 화면 모두에서 삭제한다. 상세 정보·보관기관·지도 패널·안내 문구는 유지한다.
24. **DML-089 [FRONTEND] 상세 여백 정리와 소유 확인 안내.** 상세에서만 `.detail-facts`의 상단 여백을 없애 사진과 시작 높이를 맞춘다. 하단 안내는 `이 물건이 본인의 물건이 맞는지는 보관기관에 직접 연락하거나 방문해서 확인해 주세요.`로 정리한다. 전역 스타일·다른 화면은 변경하지 않는다.
25. **DML-090 [FRONTEND] 실제 상세 보관기관 카드 정리.** 중복되는 큰 `institution-card`를 실제 상세에서 제거하고 지도 패널 아래 작은 안내로 안내문·카카오맵·공식 링크를 유지한다. 데모 경로·카드 내부 문구는 변경하지 않는다.
26. **DML-091 [FRONTEND] 직접 찾기 복귀·헤더 활성·상세 컬럼 높이.** `safeReturn()`이 `/direct-search`와 그 쿼리를 허용한다. 상세의 `?back=/direct-search`일 때 헤더는 `직접 찾기`에 active를 표시하고 `내 사진 · 내 물건 찾기`는 해제한다. `.detail-layout`은 `align-items: stretch`로 사진·정보 컬럼 높이를 맞춘다.

36. **DML-104 [FRONTEND] 페이지네이션 버튼 색상 분리.** 공용 `Pagination`에서 `[이전]`·`[다음]`은 `var(--ink)` 배경의 검은 계열, `[이동]`은 `var(--surface)` 배경의 흰 계열로 표시한다. DML-097의 세 버튼 동일 색상은 대체된다.

40. **DML-111 [FRONTEND] 직접 찾기 상단 요약 좌측·페이지네이션 우측.** 요약 두 줄(`경찰청 공개 습득물 · 필터는 현재 페이지 기준`, `전체 목록 …건 중 …페이지 · 화면 …건`)은 왼쪽, 페이지네이션은 오른쪽 끝에 배치한다. 600px 이하에서는 요약이 먼저 줄을 차지한다.

## 8. 실제 계정 인증과 계정 데이터 (로그인·회원가입·계정 찾기·저장·탈퇴) [DML-054 → 055/056 → 061~064]

### 8.1 확정 상태

- 로그인 한정으로 **6장 4항(실제 인증 기능 추가 금지)** 을 DML-054가 대체했고, 그 구현 방식을 **DML-055/056이 다시 대체**했다. 최종 상태는 아래 항목이다.
- OAuth 제공자는 **카카오 1개만**이다. 여기에 **일반 이메일 회원가입·로그인**과 **보안 질문/답변 기반 아이디·비밀번호 찾기**를 제공한다.
- 인증은 `backend/`의 FastAPI 서버가 담당한다. 사용자 계정은 SQLite에 저장하고, 비밀번호·보안 답변은 PBKDF2로 해싱하며, 세션 토큰은 해시만 DB에 둔 뒤 HttpOnly·SameSite=Lax 쿠키로 브라우저에 전달한다.
- **카카오 키는 서버 `backend/.env`에만 있다.** 브라우저는 `VITE_KAKAO_*`를 쓰지 않고, 서버가 만든 인가 URL로 이동한 뒤 코드·`state`를 다시 서버에 넘긴다. 토큰 교환·사용자 조회·세션 발급은 전부 서버에서 한다.

### 8.2 화면·경로 픽스

| 경로 | 확정 내용 |
|---|---|
| `/auth/login` | 카카오 버튼, ‘이메일로 로그인’ 전환, 이메일 로그인 폼, 회원가입 링크, **아이디 찾기·비밀번호 찾기** 링크, ‘검색으로 돌아가기’ 버튼 |
| `/auth/signup` | 이메일·닉네임(선택)·비밀번호·비밀번호 확인·**보안 질문 선택·답변 입력** |
| `/auth/find?mode=email` | 닉네임+보안 질문+답변으로 가입 이메일 표시 |
| `/auth/find?mode=password` | 이메일+보안 질문+답변+새 비밀번호로 재설정, 기존 세션 종료 |
| `/auth/kakao/callback` | 카카오 콜백 처리 후 `safeReturn()`으로 복귀 |
| `/account` | 로그인 사용자 닉네임·이메일·제공자·회원가입일·최신 방문일, 프로필 수정, 로그아웃, 계정 탈퇴 |

- ‘검색으로 돌아가기’와 로그인/회원가입 화면의 ‘돌아가기’ 버튼은 **짙은 잉크색(`button--ink`)** 이다. 흰색으로 되돌리지 않는다.
- 회원가입·로그인·계정 찾기 입력창은 `.login-form` 안에서 **간격을 좁게 유지**한다. 필드마다 24px 마진을 다시 넣지 않는다.
- `safeReturn()` 화이트리스트(`/gallery|lost-found|history|valuables|settings|account`)와 `returnTo` 인코딩은 그대로다. 외부 URL은 `/valuables`로 떨어뜨린다.
- `AuthGate`, F3 로그인 가드, 44px/48px 버튼, `.login-panel` 기본 스타일은 유지한다.

### 8.3 데이터 경계 (변경 금지)

- 계정 서버에 저장되는 것은 **이메일·닉네임·비밀번호 해시·보안 질문/답변 해시·세션·카카오 제공자 ID** 뿐이다.
- **F1/F2/F3 사진 원본과 사진별 검색정보는 계정과 무관하게 브라우저 임시 상태다.** 서버에 업로드·저장하지 않고, 회원가입·로그인·계정 찾기로 인해 초기화 정책이 바뀌지 않는다.
- 로그아웃 시 F3 로컬 상태를 초기화하는 기존 동작은 유지한다. 단, 계정에 저장된 항목까지 지워지지 않는다(DML-064).
- **DML-061 대체**: 로그인 상태의 ‘찾은 기록’과 ‘사진 등록해 두기’ 항목은 계정에 저장된다. 아래 “계정 서버에 저장되는 것은 인증 정보 뿐”이라는 설명은 **계정 저장 기능 추가 전 시점의 경계**로 이해하고, 현재 경계는 8.5를 따른다. F1/F2 검색 입력·참고 사진·갤러리 원본은 여전히 서버에 저장하지 않는다.

### 8.4 환경설정·검증 메모

- 서버 env: `KAKAO_JAVASCRIPT_KEY`, `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`, `KAKAO_REDIRECT_URI`, `GEUGEO_ALLOWED_ORIGINS`, `GEUGEO_COOKIE_SECURE`, `GEUGEO_DATA_DIR`. 프론트 env 파일은 두지 않는다.
- 카카오 인가 스코프는 **`profile_nickname`, `profile_image` 두 개만** 요청한다. 콘솔에 권한이 없는 `account_email`은 요청하지 않으며, 카카오 계정 이메일은 저장하지 않는다(DML-057).
- 카카오 콘솔 Redirect URI는 `http://127.0.0.1:5173/auth/kakao/callback`과 정확히 일치해야 한다. 미등록 시 `KOE006`이 반환된다. 등록 후 동의 화면까지는 정상 도달을 확인했다.
- 토큰 교환에는 REST API 키의 **클라이언트 시크릿**이 필요하다. 콘솔의 앱 > 플랫폼 키 > REST API 키 > 클라이언트 시크릿에서 발급받아 `backend/.env`의 `KAKAO_CLIENT_SECRET`에 넣고 서버를 재시작해야 한다. 비어 있으면 `KOE010(invalid_client)`이 반환되고 화면에 오류 코드가 함께 표시된다(DML-059).
- 사용자 정보 조회의 `property_keys`는 **`["kakao_account.profile"]` JSON 배열 문자열**로 전달한다(DML-060). 리스트를 그대로 넘기면 사용자 정보 조회가 실패한다.
- 백엔드 미실행으로 프록시가 502를 반환하면 '서버에 연결하지 못했어요. 백엔드가 실행 중인지 확인해 주세요.'를 표시한다(DML-058). `npm run dev`는 백엔드를 자동 실행하므로, 기존 개발 서버는 재시작해야 한다.
- 백엔드 테스트 14개, 프론트엔드 `typecheck`·`lint`·`test`(358개)·`build` 통과. 빌드 산출물에 카카오 키·`VITE_KAKAO_*` 문자열이 없다.
- **실제 카카오 OAuth 로그인 성공 검증 완료**: Redirect URI 등록 + `KAKAO_CLIENT_SECRET` 설정 + `property_keys` JSON 배열 형식 수정 후, 인가 → 콜백 200 → `/valuables` 이동 → `/api/auth/me`가 `provider='kakao'` 반환까지 확인했다(DML-059/060). 이메일은 요청하지 않으므로 `email=''`이다. 서버 키가 없으면 503(`kakao_not_configured`)을 반환한다.

### 8.5 계정 데이터 영속·프로필·탈퇴 [DML-061~065]

- 서버 엔드포인트: `GET/PUT /api/me/content`(계정별 기록·등록 물건), `PATCH /api/me/profile`(닉네임·프로필 이미지), `DELETE /api/me`(계정 탈퇴). CORS는 `PUT`/`PATCH`/`DELETE`를 허용한다.
- 계정 콘텐츠는 `user_content.payload_json`에 저장한다. 사진 `File`은 data URL로 직렬화하고 복원 시 `File`로 되돌린다. 로그인 전 로컬 작업은 최초 로그인에 이관하되 `id` 중복은 합치고 데모 시드는 제외한다.
- 로그인 후 변경은 디바운스로 서버에 동기화한다. 로그아웃은 `signOut()`만 호출하고 `user === null` 이펙트가 로컬 상태를 초기화한다(DML-064). 계정 저장 데이터는 로그아웃해도 남는다.
- 카카오 재로그인은 닉네임·프로필 이미지를 덮어쓰지 않는다. 사용자가 `/account`에서 수정한 값이 유지된다(DML-062).
- `/account` 프로필 편집은 미리보기와 사진 선택을 묶은 별도 영역, 닉네임과 저장 동작을 담은 편집 영역으로 정돈한다. 모바일에서는 세로 흐름으로 전환한다. 기존 8MB 제한·접근 가능한 파일 선택·프로필 저장/이미지 제거 동작을 유지한다(DML-065).
- 탈퇴는 **‘계정을 탈퇴합니다’** 정확 입력 후 확인 창에서 확정한다. 서버는 계정·세션·콘텐츠를 삭제하고 기기 원본은 남긴다(DML-063).
- 검증: 로컬→계정 이관·중복 제거·데모 시드 제외, 새로고침/재로그인 영속, 프로필 저장, UI 로그아웃 401, 카카오 재로그인 시 수정 프로필 유지, 탈퇴 후 DB 행 제거까지 브라우저에서 확인. 백엔드 `pytest` 20개, 프론트 `typecheck`·`lint`·`test`(15파일 363개)·`build` 통과, 빌드 산출물에 카카오 키·`VITE_KAKAO_*` 문자열 없음 확인.

## 9. 멀티모달 AI 검색 파이프라인 [DML-20261120-087]

### 9.1 적용 범위와 데이터 동의

- `/direct-search`는 우선 일반 검색어와 경찰청 공개 정보 필터를 사용한다. 이 화면의 AI 검색·참고 사진 UI는 아직 연결하지 않으며, 공개 API 결과는 기존처럼 공개 정보 순서로 표시한다.
- F1 `/gallery`·`/gallery/results`, F2 `/lost-found`·`/lost-found/results`의 AI 조건 정리와 검색 도우미는 사용자가 **분석 동의**를 누른 경우에만 외부 AI를 호출한다. 검색 원문과 사용자가 첨부한 참고 사진만 전송한다. 연결된 F1 갤러리 전체 파일은 조건 정리 요청에 포함하지 않으며, 서버는 요청 내용을 저장하지 않는다. 외부 제공자의 데이터 처리·보존 정책은 별도로 안내한다.
- AI 계획에는 원문과 `종합`, `이미지`, `문맥·조건` 채널의 검색어·키워드, 추출 가능한 분류·지역·방향·날짜 필터가 포함된다. 결과 요약에 계획을 보여주고 F2는 종합 검색어를 공개 API 조회에 적용한다. 결과는 동일 실물이라는 보장이나 회수 보장을 하지 않는다.
- 후보 사진 비교(이미지 분석) 백엔드 API는 준비되어 있으나 F1/F2 결과의 이미지 점수화·정렬은 **미연결**이다. F2 문맥 텍스트 순위화는 DML-113에서 별도 범위로 연결했으며, 이미지 분석까지 연결된 것으로 표현하지 않는다.
- 최신 DML-100: `/direct-search` 검색 UI는 간결한 한 줄 일반 검색과 현재 페이지 기준 필터다. 물품 분류·분실 예상 지역·습득일 범위·현재 페이지 데이터에서 만든 색상 드롭다운을 제공한다. 공개 API 후보에 방향 메타데이터가 없어 이 화면에서는 방향 필터를 보이지 않는다. DML-085의 여러 줄 입력 대체는 직접 찾기에만 적용되며 F2 입력은 유지된다. 실제 API 순서·AI 미연결 경계는 바꾸지 않는다.
- 최신 DML-102: 검색과 필터를 분리된 좌우 카드가 아닌 단일 전체 폭 패널 안에서 위아래로 배치한다. 5개 필드는 큰 화면에서 한 줄, 작은 화면에서 3·2·1열로 전환한다.
- 최신 DML-105: 검색·필터 패널은 한 줄 검색과 접힌 조건 요약을 유지하며 스크롤 중 상단 고정한다. 펼친 조건은 데스크톱에서 분류·지역·색상·습득일 범위를 한 줄로 표시하고 작은 화면에서 재배치한다. 드롭다운은 아래로 열리고, 날짜는 `YYYY/MM/DD`로 입력해 ISO 형식으로 적용한다. 초기화·조건 적용은 오른쪽 아래에 둔다.
- 최신 DML-106: `[검색 조건]` 토글과 `[초기화]`·`[조건 적용]`을 한 행에 배치한다. 초기화는 미적용 초안을 비우고 편집 패널을 연다.
- 최신 DML-107: 모바일 `/direct-search`의 물품 카드는 88px 이미지 왼쪽·정보 오른쪽으로 표시한다. 데스크톱 및 다른 화면의 카드에는 적용하지 않는다.

### 9.2 OpenAI 모델·서버 설정

- 사용자가 OpenAI API의 GPT-6 Luna를 선택했다. 모델 ID는 `gpt-6-luna`이며 LLM 검색어 정리, VLM 참고 사진 설명, 비전 후보 비교의 기본값으로 둔다. OpenAI 공식 모델 문서에서 이미지 입력과 Chat Completions 지원을 확인했다.
- 키는 서버 `backend/.env`의 `OPENAI_API_KEY`에만 둔다. 사용자는 키 하나로 세 역할을 설정하는 방식을 선택했다. 키·모델 토큰을 프론트 번들 또는 브라우저에 노출하지 않는다. 모델별 API 키·호환 엔드포인트는 역할별 서버 설정으로 나중에 교체할 수 있다.
- `GET /api/ai/status`는 키를 노출하지 않고 역할별 준비 상태를 반환한다. `POST /api/ai/search/prepare`는 명시 동의를 확인한 뒤 조건 초안을 반환한다. `POST /api/ai/vision/compare`는 동의를 확인하고 후보 이미지 비교를 수행한다. 요청은 이 애플리케이션의 영속 저장소에 기록하지 않는다.
- 프롬프트 파일은 `backend/prompts/`에서 수정한다. 키 미설정·제공자 오류·시간 초과는 성공처럼 처리하지 않고 구분된 오류로 반환한다. 상태 조회는 모델 역할별 준비 상태만 반환하며, 실제 GPT-6 Luna 요청은 아직 수행·검증하지 않았다.
- DML-087은 이 확정문서의 이전 “AI/VLM 미연결 유지” 문구 중 **AI 조건 초안 범위만** 대체한다. 일반 직접 찾기 검색·필터 정책과 후보 점수화 미연결 상태는 유지한다.

### 9.3 F2 자연어·주변 장소 검색 요구사항 [DML-20261120-101]

- 검색 해석은 일부 구조화 필드만 추출하는 데 그치지 않고 사용자 원문과 상세 자연어 설명을 함께 고려해야 한다. 특히 `field__help detail-description`의 상세 설명 및 물건 설명·조건을 검색 맥락에서 누락하지 않는다.
- “정확하지는 않지만 신림역 인근에서 잃어버렸다” 같은 모호한 위치 표현은 습득 장소, 보관 장소·기관, 소재지·주소의 근접 후보까지 의미 기반으로 고려한다. 장소명 완전 일치만 요구하지 않는다.
- 주변 장소는 추론 후보이며 실제 분실·습득 위치로 단정하지 않는다. 결과 정렬에 반영할 때는 근거와 불확실성을 전달한다. DML-113에서 `/lost-found/results/context`에 현재 페이지 최대 12개 후보의 텍스트 순위화를 연결했다. 매 실행마다 별도 동의 후 검색 문장·적용 조건·AI가 참고 사진에서 만든 특징 설명(있는 경우)·공개 후보 텍스트를 외부 AI에 보낸다. 원본 사진·전화번호는 포함하지 않는다. 결과는 접을 수 있는 근거·장소 관계·불확실성과 함께 제시하며, 점수는 일치 확률·동일 물건·소유권·회수 보장이 아니다.
- 구현 검증은 모의 AI 응답으로 한정된다. 실제 GPT-6 Luna 요청, 검색 품질, 실기기/브라우저 결과는 검증하지 않았으므로 운영 연결·정확도 완료를 주장하지 않는다. `/direct-search`는 사용자가 별도 변경을 지시하기 전까지 일반 검색·필터만 제공한다.

### 9.4 F2 검색 제출과 첫 페이지 자동 순위화 [DML-20261120-115]

- `[비슷한 물건 찾기]` 제출 한 번으로 명시 동의 → AI 검색어 해석 → 경찰청 공개 API 검색 → 첫 결과 페이지 후보 자동 순위화가 이어진다. F2 입력에 별도 `[AI로 조건 정리]` 동작을 추가하지 않는다.
- 동의 범위에 검색 원문·선택 참고 사진의 AI 해석과 첫 결과 페이지의 공개 후보 텍스트(최대 12개)를 포함한다. 후보의 상세 설명·특이사항·습득/보관 장소·주소 등을 순위화에 사용하며 후보 사진 원본·전화번호는 전송하지 않는다. 앱 메모리의 일회성 동의 상태는 검색 기록·URL에 저장하지 않는다.
- 자동 요청은 AI 검색 필터와 결과 데이터가 준비된 뒤 시작하며, 응답 전에는 공개 API 순서를 유지하고 성공 응답 후 관련 점수가 높은 후보를 위로 올린다. 실패 시 오류와 재시도 경로를 보이고 공개 API의 기존 순서를 임의로 대체하지 않는다. 첫 페이지 외 수동 비교는 별도 사용자 동의를 요구한다.
- 이 흐름은 텍스트 문맥 순위화이며 사진 후보 이미지 분석·전체 결과의 무제한 순위화를 뜻하지 않는다. 실제 GPT-6 Luna 호출·검색 정확도·브라우저/실기기 사용성은 미검증이다. 직접 찾기와 F1 검색의 AI 동작은 변경하지 않는다.

## 10. 갤러리 사진 분석·3축 정렬·클립보드 [DML-20261120-117~119]

- 위 9.1의 'F1 이미지 점수화·정렬 미연결'과 9.4의 'F1 검색 AI 동작 변경 없음'은 **DML-117로 대체**된다. 최신 로그는 `10_디자인_마스터_작업로그.md`의 DML-117~119다.
- `/gallery`에는 `[AI로 조건 정리]` 버튼이 없다. 대신 참고 사진과 검색어를 넣고 `[사진 찾기]`를 누르면 연결 갤러리 사진(최대 12장)을 `/api/ai/vision/compare`로 분석한다.
- 결과 화면의 세 채널은 각각 **종합 관련성(`score`) / 이미지 유사도(`imageSimilarity`) / 맥락 관련성(`contextRelevance`)** 순서다. 분석 실패 시 순위를 바꾸지 않고 오류와 `[사진 분석 다시 시도]`를 표시한다. 분석 중에는 안내 문구를 보여준다.
- 참고 사진은 `[참고 사진 추가]` 버튼 외에 검색 textarea로 이미지를 붙여넣어도 추가된다. 같은 동작이 `/lost-found`에도 적용된다. 텍스트와 이미지가 함께 붙여넣어지면 이미지 파일만 참고 사진으로 쓴다.
- AI가 참고 사진에서 읽은 대상·요소(`referenceDescriptions`)는 결과 상단 `[참고 사진 분석]`에 표시되고, 검색 문장과 함께 3축 채점에 반영된다. F2는 기존 `[참고 사진에서 읽은 특징]` 표시를 유지한다.

## 11. F2 자연어·AND/OR/NOT·사진 특징 맞춤 검색 [DML-20261120-120]

- 경찰청 공개 API는 `PRDT_NM` 한 단어만 받아 자연어 문장 전체를 넣으면 0건이 된다. AI가 자연어와 참고 사진 분석에서 **탐색어 / AND / OR / NOT / 사진 특징**을 분리하고, 서버가 공개 응답 JSON 전체 텍스트에 이를 적용한다.
- 조건 계약: `AiSearchCriteria = { apiKeywords(≤3), include(AND), any(OR), exclude(NOT), imageFeatures(≤8) }`. `apiKeywords`는 넓은 후보 조회용 명사이고, 나머지는 JSON 텍스트 필터·점수용이다. 조건이 없거나 AI가 실패하면 원문 검색으로 폴백해 공개 목록이 막히지 않는다.
- F2 흐름: `LostSearchComposer` 제출 → `prepareAiSearch('lost', ...)` → `draft.aiPlan.criteria` → `LostSearchResults`가 `criteriaFromPlan()`으로 조건을 정규화 → `resolveApiKeyword()`로 대표 탐색어 결정 → `searchLostFound(keyword, page, rows, hints)`로 조건 전달 → `applyCriteria()`가 NOT 제외·관련도 정렬·근거 계산 → 세 채널 렌더.
- `apiKeywords` 여러 개는 서버가 `PRDT_NM`에 OR로 조회·병합한다. 항목의 물품명·내용·특이사항·분류·색상·습득/보관 장소·기관·주소·상태를 합친 텍스트에 AND/OR/NOT·사진 특징을 적용하며, 띄어쓰기가 다른 복합어는 각 어절이 모두 있으면 일치로 본다. NOT 조건에 걸린 항목만 제외하고, 조건 미일치 항목은 넓은 결과로 유지한다.
- 조건 카드(`[AI가 공개 정보에서 읽은 맞춤 조건]`)와 AI 도우미 요약에 다섯 그룹을 칩으로 표시한다. AI가 추천한 장소가 시도 단위(`REGIONS`)가 아니면 URL 지역 필터로 넣지 않고 JSON 조건 매칭에만 사용한다. 이전 기록은 채널 계획의 질의·키워드로 조건을 유도한다.
- 직접 찾기는 이 변경의 대상이 아니었다. AI 점수·재정렬 없이 공개 API 순서를 유지하며, 전체 API 필터·건수/페이지 재계산은 별도 P0 작업으로 분리했다(12장에서 완료).
- 검증: `typecheck` 통과, Vitest **22개 파일·421개 테스트 통과**, 백엔드 pytest **53개 통과**. 브라우저 실측에서 자연어 AND/OR/NOT과 사진 특징이 조건 카드·결과에 반영됐다.
- 검증: 프론트 `typecheck`·`lint`·Vitest **410개 통과**, 백엔드 pytest **47개 통과**. 브라우저 실측에서 채널별 순서 차이와 붙여넣기 첨부를 확인했다. 직접 찾기의 전체 필터·AND/OR/NOT 요구는 12장에서 처리했다.

## 12. 직접 찾기 전체 필터·필터 기준 건수·AI 조건 분석 [DML-20261120-121]

- `/direct-search`의 세 결함을 해소했다. ①필터가 현재 페이지에만 적용되던 문제, ②건수·페이지 수가 필터 전 API total을 쓰던 문제, ③AI 분석이 없던 문제.
- 서버 `POST /api/lostfound/browse`가 핵심이다. 요청은 `{ keyword, page, rows, maxPages, hints, filters }`이고, 서버는 두 공개 소스를 최대 20페이지(요청에 따라 최대 50)까지 병렬 스캔한 뒤 전체 풀에 필터를 적용한다. `filters`는 분류·색상·지역·습득 시작/종료일이며, URL 쿼리값이 그대로 전달된다.
- AI는 `prepareAiSearch('direct', keyword, [])`로 자연어를 해석해 `criteria`를 만든다. `apiKeywords`로 넓게 조회하고 `include(AND)`/`any(OR)`/`exclude(NOT)`/`imageFeatures`를 공개 JSON 전체 텍스트의 하드 필터로 적용한다. AI 실패 시 조건을 비우고 원문 검색으로 폴백한다. 분석이 끝나기 전에는 조회하지 않아 원문 결과가 먼저 깜빡이지 않는다.
- 순위 정책은 바뀌지 않는다. AI 점수로 재정렬하지 않고 공개 API의 습득일·ID 순서를 유지한다. `matchScore`/`aiMatch.hits`는 근거 표시용이다. 조건 미일치 항목은 직접 찾기에서 제외되며, AI 실패 시에는 공개 목록이 유지된다.
- total은 스캔한 풀에 필터와 중복 제거를 적용한 건수로 다시 계산한다. 중복 제거는 프론트 `dedupeLostFound()`와 같은 기준(물품명·색상·분류·습득일·보관장소)을 서버에도 적용해 total과 화면 건수를 일치시켰다. `pages = ceil(total / rows)`이고 현재 페이지 슬라이스도 같은 필터 결과에서 가져온다.
- 화면에는 스캔 건수, 적용 필터 수, `앞쪽 기준` 여부, 조건 카드(5개 그룹), 필터 기준 건수와 화면 건수를 표시한다. 상단 배치·버튼 색상·카드 크기 등 DML-104~112의 확정 레이아웃은 변경하지 않았다.
- 검증: 프론트 `typecheck` 통과, Vitest **22개 파일·422개 테스트 통과**, `npm run build` 성공, 백엔드 pytest **59개 통과**. 실호출은 색상 필터 240건 스캔 → 59건, 자연어 hints 240건 스캔 → 5건을 확인했다.
- 브라우저 실측: 분류 `지갑` 필터에서 432건·11페이지·화면 40건이 일치하고 2페이지 이동도 유지된다. 자연어 '신림역 근처 … 검은 가죽 지갑 … 파손된 건 아니에요'에서 AI가 `apiKeywords=지갑`, `AND=[가죽,지갑]`, `OR=[검정,검은색,블랙,신림역 근처]`, `NOT=[파손]`을 만들어 5건을 표시했다.
- 모델 선택: F2는 기능 이름이고 특정 비전 모델이 아니다. 현재 LLM/VLM/Vision 세 역할 모두 `openai-compatible`의 `gpt-6-luna`를 쓰지만, 서버 .env의 `GEUGEO_AI_<ROLE>_PROVIDER/_MODEL/_BASE_URL/_API_KEY`로 교체 가능하다. YOLOE는 객체 탐지 모델이라 현재 chat/completions 계약에 직접 넣을 수 없고, 별도 감지 서비스의 라벨을 LLM 조건 분석에 넘기는 확장이 필요하다.

## 15. 이관 시점 상태 보완 [DML-20261123-130]

- 위 13장의 'LLM/VLM/Vision 세 역할' 문구는 **DML-123으로 대체**됐다. 현재 역할은 `multimodal`과 `imageSimilarity` 두 개이고, `llm`/`vlm`/`vision`은 호환용 별칭이다.
- 위 13장의 'YOLOE는 chat/completions에 직접 넣을 수 없어 별도 감지 서비스가 필요하다'는 문구도 **대체**됐다. YOLOE는 크롭 1단계로만 쓰고 사전학습 가중치를 그대로 사용한다. 객체 ≥2개 또는 종류 ≥2가지일 때만 자르며 VLM census가 판정을 보강한다(DML-125/126/127).
- 위 9.1·9.4의 '이미지 점수화·정렬 미연결' 문구는 **DML-123/128로 대체**됐다. 공개 사진/설명 대조와 점수·정렬은 연결됐고, 실측 이미지 R@1 1.000을 확인했다. 다만 확정 4개 영역의 레이아웃·카피·카드 크기·상태 정의·데이터 경계는 바꾸지 않았다.
- 위 12장의 'AI 미연결 안내' 문구는 **DML-116으로 이미 대체**됐다. AI 안내·동의는 팝업이 아니라 `/lost-found` 하단 요약이며, 실패 시 원문 검색으로 폴백한다.
- 이관 런북·현재 아키텍처·검증 수치는 `14_코덱스_이관_핸드오프.md`에 정리했다. 이 절은 기존 항목을 삭제하지 않고 대체 관계만 추가한다.

## 13. 결과 섹션 순서와 구분선 정리 [DML-20261121-122]

- 결과 화면의 세 섹션 순서를 `종합 → 설명·조건이 비슷한 후보 → 사진 특징이 비슷한 후보`로 바꿨다. 순서는 `lost-result-model.ts`의 `LOST_RESULT_CHANNELS`가 단일 원천이고, CSS `order` 강제는 없다.
- `gallery-search.css`에서 섹션 사이 `gap:32px`를 제거하고 두 번째·세 번째 섹션에만 위쪽 1px 선과 32px 여백을 적용했다. 첫 섹션은 선·여백 없음, 마지막 섹션은 아래 여백 없음(아래 선은 기존 `.result-disclaimer`가 담당). 좁은 화면은 24px로 줄인다.
- 확정 4개 영역의 레이아웃·카피·카드 크기·상태 정의·데이터 경계는 바꾸지 않았다. 브라우저 실측으로 제목 순서와 `border-top=[0,1,1]px`, `padding-top=[0,32,32]px`를 확인했다.
- 검증: 프론트 `typecheck`·`lint` 통과, Vitest 22개 파일 422개 테스트 통과, `npm run build` 성공.

## 14. 멀티모달·유사도 전용 비전 재구성 [DML-20261121-123]

- AI 역할을 `multimodal`(자연어·이미지·joint 해석)과 `imageSimilarity`(사진 임베딩 유사도) 두 개로 재정의했다. 기존 `LLM/VLM/VISION` 문자열은 호환용 별칭으로 `multimodal`에 매핑된다. 전용 유사도 미설정(`GEUGEO_AI_SIMILARITY_PROVIDER=none`)이면 멀티모달이 사진 대조를 맡는다.
- `ai-search-api.ts`에 `matchPublicItemImages()`와 `AiVisualMatchResult/Response` 타입을 추가했다. `LostSearchResults.tsx`는 현재 공개 후보 최대 12건(사진 후보 우선, 부족하면 설명만 있는 항목 포함)의 `imageUrl`+공개 텍스트를 `POST /api/ai/vision/match-public`으로 보내 0~100 유사도를 받는다.
- 결과는 `사진 특징이 비슷한 후보` 정렬의 1차 점수, `종합` 정렬의 결합 점수로 쓴다. 맥락 채널은 기존 AI 순위를 유지한다. 요청 시퀀스 가드와 Scope 키로 StrictMode 중복· stale 응답을 막고, 실패 시 기존 공개 순서·맥락 순서로 폴백한다. 상태 문구에 분석 주체(전용 비전/멀티모달)를 표시한다.
- 갤러리 `compareCandidates()`는 `imageSimilaritySource`를 파싱해 `GallerySearchResults.tsx`에서 유사도 분석 주체를 툴바에 표기한다. `interpret_search.txt`는 참고 사진이 없어도 자연어에서 `imageFeatures`를 뽑도록 갱신했다('딸기가 그려진 지갑' → 딸기 그림·지갑).
- 검증: 백엔드 pytest 66개, 프론트 typecheck·lint 통과, Vitest 22개 파일 424개 테스트 통과, `npm run build` 성공. 브라우저에서 '딸기가 그려진 지갑' 검색 시 사진·설명 비교 상태와 재정렬을 확인했다.

## 16. 검색 UX 점검 후 보완 [DML-20261124-131]

- 직접 찾기의 표시 페이지는 실제 결과 범위 안에서 보정한다. 빈 결과의 ‘전체 목록 보기’는 검색어와 조건을 지운다. 목록 출처 중복과 중복 진행 안내를 제거하고 카드별 매칭 근거는 유지한다.
- F2 결과에서 적용 조건의 일치 건수는 한 줄로 먼저 표시하며, 세부 조건은 기본 접힘으로 제공한다. 모바일에서 ‘검색 도우미’와 보조 동작 ‘새 후보 확인’을 한 줄로 배치한다. 새 후보 확인 결과를 명시하며, 다음 페이지의 실패는 자동 반복 없이 재시도 또는 이전 결과 복귀로 안내한다.
- 같은 화면에서 검색 버튼을 연달아 눌러도 검색 기록은 한 번 저장한다. 비로그인 기록의 새로고침 시 소멸을 안내한다. 기존 색상 필터의 적용 화면과 계정 데이터 저장 동작은 별도 검토 사항이다.
- 공통 로그인 화면의 제목은 ‘로그인’이며 보관함에서 로그인으로 이어지는 화면은 보관함 맥락의 제목과 설명을 유지한다. 회원가입의 보안 질문 답변 설명은 계정 찾기에 사용하는 목적을 안내한다.

## 17. 비로그인 검색 기록과 공개 조회 범위 [DML-20261124-132·133]

- F1·F2 비로그인 검색 기록과 결과는 같은 브라우저에서 새로고침해도 복원한다. 16절의 기록 소멸 안내는 이 변경으로 대체한다. 로그인 뒤에도 브라우저에 저장한 기록을 이어볼 수 있으며, 이 기록과 사진은 자동으로 계정에 업로드하지 않는다. 로그인 상태에서 만든 계정 기록은 계정에서 불러온다.
- 검색 수정은 같은 기록에 저장한다. 삭제는 선택한 기록과 그 결과의 브라우저 저장본에 적용한다. 파일이 포함된 검색은 사진과 방향, 연결 갤러리의 하위 폴더 경로를 유지한다.
- 분실물 입력·결과·직접 찾기에는 검색 출처를 ‘경찰청·포털기관 공개 습득물’로 표시한다. F2는 출처·검색어별 API 페이지를 이어서 조회하며, 일부 공개 목록 오류는 재시도할 수 있다. 스캔 상한이 있는 화면은 확인한 범위를 표시하고 공식 검색으로 연결한다.
- 모바일 직접 찾기의 검색·조건 버튼은 44px 높이로 표시한다. 기존 검색 모드의 버튼 강조와 결과 카드 배열을 따른다.

## 18. 사진 보관함의 응답·편집 상태 [DML-20261124-134]

- 보관함 직접 진입 시 계정 불러오기 상태를 표시한다. 불러오기 오류는 재시도할 수 있다. 계정 응답 전에는 물건의 저장·삭제 완료를 표시하지 않으며, 실패하면 확인 창과 입력을 보존한다.
- 사진이 없는 기존 항목은 대체 표시를 제공한다. 사진 6장 상태에서는 ‘사진 편집’으로 기존 사진을 편집할 수 있다. 편집할 때 큰 사진·파일명 다음에 썸네일을 표시하고, 모바일에서 긴 파일명은 두 줄까지 보인다.

## 19. 동일 참고 사진 우선 표시 [DML-20261124-135]

- 연결된 전체 사진에서 파일 내용이 같은 참고 사진을 찾아 세 결과 섹션과 더보기에서 우선 표시한다. 동일 파일 확인은 브라우저에서 진행한다. 다른 후보의 AI 비교는 요청당 최대 12장과 기존 채널별 점수 기준을 따른다.
- 참고 사진의 특징은 결과의 검색 요약 아래 제목과 문단으로 표시한다. 같은 파일로 확인된 카드에만 ‘참고 사진과 같은 이미지’ 라벨을 표시한다.

## 20. 전체 갤러리 검색과 결과 카드 간격 [DML-20261124-136]

- 갤러리 검색은 연결한 모든 파일을 같은 후보 모집단으로 사용한다. 기기 내 모델이 읽을 수 있는 사진을 비교하고, 분석하지 못한 사진이 있으면 건수를 표시한다. 세 채널의 미리보기와 더보기는 전체 비교 결과에서 가져오며, 페이지당 12장을 표시한다. 같은 파일은 세 채널에서 우선 표시한다.
- 갤러리·분실물 결과의 검색 요약, 정리한 검색 조건, 검색어 다듬기 카드 사이 간격은 PC 16px, 모바일 12px다. 검색 조건 카드를 펼쳐도 같은 간격을 사용한다.

## 21. 찾은 기록의 추천 사진 미리보기 [DML-20261124-137]

- 갤러리 검색 기록의 미리보기는 해당 기록의 ‘추천 사진’ 1위를 사용한다. 검색 수정이나 재검색으로 1위가 바뀌면 같은 기록의 미리보기에 반영한다. 1위 사진을 불러올 수 없을 때는 기본 아이콘을 표시한다.

## 22. 분실물 후보의 검색과 조건 배치 [DML-20261124-138]

- 분실물 후보 화면에서 검색어, ‘AI로 검색어 다듬기’, ‘검색 수정’을 한 패널에 두고 바로 아래에 ‘검색 조건’과 ‘새 후보 확인’을 표시한다. 모바일 검색 도우미는 제목 영역에서 연다.
- ‘정리한 검색 조건 보기’와 ‘공개 정보에 적용한 조건’은 후보 목록 아래의 접힌 영역으로 표시한다. 검색 출처는 제목 아래에서 확인하고, 일치 건수와 완료된 비교의 설명은 하단에서 확인한다.

## 23. 분실물 결과의 동일 사진 정리 [DML-20261124-139]

- 분실물 후보의 각 목록에서 사진 주소나 제목이 달라도 사진 내용이 같으면 현재 필터·순위 기준의 첫 카드 한 건을 표시한다. 서로 다른 사진이나 사진을 확인할 수 없는 별개 기록은 제목이 같아도 각각 표시한다. 동일 공개 기록 ID는 한 번만 표시한다.
- 더보기는 중복을 정리한 목록을 페이지로 나눈다. 새 후보 확인도 이전 후보와 동일한 사진을 건수에서 제외한다.

## 24. 분실물 결과의 세 기준과 사용자 필터 [DML-20261124-140]

- ‘추천 후보’는 사진이나 설명 중 강한 근거를 반영하고, 두 근거가 있으면 함께 평가한다. ‘사진이 닮은 후보’는 실제 공개 사진을 입력한 묘사 및 참고 사진과 대조한다. ‘설명이 잘 맞는 후보’는 공개 설명과 장소 정보를 비교하며 사진이 없는 항목도 포함한다.
- 글만, 사진만, 글과 사진을 함께 입력하는 세 경우에 세 결과 구역을 보여준다. 첨부한 참고 사진 전체를 비교한다. AI의 분류·지역·기간·방향 추정값은 제안으로 표시한다. 필터는 사용자가 선택한 값만 후보를 제한한다.
- ‘직접 찾기’의 ‘빠른 검색’은 공개 원문을 비교하고 ‘자세히 찾기’는 설명과 공개 사진을 함께 살핀다. 후보 목록 하단의 비교 상세 영역은 ‘후보를 찾는 데 쓴 단서’로 표시한다.

## 25. 직접 찾기 검색 방식 선택과 사진 결과 표시 [DML-20261124-141]

- 직접 찾기 검색창 위에 ‘일반 검색’과 ‘AI 검색’을 표시한다. 처음에는 AI 검색을 선택한다. Enter와 검색 버튼은 선택된 방식을 실행하며, 입력 아래의 안내와 결과의 검색 방식 표기는 실제 동작과 일치한다.
- AI 검색에서 사진 비교를 마친 후보는 ‘먼저 찾은 후보’에 먼저 표시하고, 최종 결과가 준비되면 전체 목록으로 바꾼다. 분실물 찾기에서도 비교가 끝난 후보부터 사진 결과와 추천 결과에 표시한다.

## 26. 직접 찾기 검색바 배치 [DML-20261124-142]

- 데스크톱 검색바는 ‘일반 검색·AI 검색’ 선택, 입력창, 실행 버튼, ‘전체 보기’를 한 줄에 둔다. Enter 표시는 실행 버튼에 넣는다. 모바일에서는 검색 방식 선택을 위에 두고, 입력창과 버튼을 다음 줄에 둔다. Enter는 선택된 방식을 실행한다.

## 27. 직접 찾기 검색 방식 순서 [DML-20261125-143]

- 데스크톱과 모바일 모두 왼쪽부터 ‘AI 검색’, ‘일반 검색’ 순으로 표시한다.

## 28. 직접 찾기 AI 검색 로딩 [DML-20261125-144]

- 실행한 AI 검색의 진행 상태는 로봇이 물건을 찾는 애니메이션으로 표시한다. 일반 검색과 전체 목록 조회는 기본 진행 표시를 사용한다. 검색 방식 선택만 바꿨을 때는 실행 중인 검색에 맞춰 진행 표시를 유지한다.

## 29. AI 검색 중 일반 검색 결과 [DML-20261125-145]

- ‘직접 찾기’의 AI 검색에서 같은 검색어·사용자 필터의 일반 검색 결과를 먼저 볼 수 있다. 기본 미리보기는 PC 4건·모바일 2건까지이며 같은 자리에서 펼치거나 접는다. AI 검색이 끝나도 일반 검색 결과와 펼침 상태를 유지한다.

## 30. 하단 일반 검색의 키워드 보완 [DML-20261125-146]

- AI 검색의 하단 일반 검색 결과가 문장 조회에서 0건이면, 같은 사용자 필터로 짧은 물품 키워드를 다시 조회한다. 공개 정보에서 색상과 무늬 등 다른 단서가 일치하는 후보를 우선하고, 실제로 사용한 키워드를 표시한다.

## 31. AI 추가 검색 결과 누적 [DML-20261125-147]

- ‘더 찾아보기’ 중 기존 결과와 페이지를 유지한다. 기존 후보와 새 후보를 합쳐 관련도 순으로 배치하고 페이지 수를 갱신한다. 실패해도 기존 목록에서 계속 탐색할 수 있다.

## 32. 분실물 추천 검색 문구 편집 [DML-20261125-148]

- ‘AI로 검색어 다듬기’로 만든 문구는 사용자가 편집할 수 있다. ‘이 문구로 다시 검색’을 눌렀을 때 확정하며 편집한 문구와 그 문구를 기준으로 만든 탐색 조건으로 같은 기록을 갱신한다.

## 33. 다듬은 검색 문구 접기 [DML-20261125-149]

- 분실물 결과에서 새 추천 문구는 펼쳐서 보여준다. 접었다가 다시 펼쳐도 편집 중인 문구는 남는다.

## 34. 검색어 다듬기 열기와 추천 생성 분리 [DML-20261125-150]

- 분실물 결과의 ‘AI로 검색어 다듬기’는 패널의 열기와 닫기를 맡는다. 패널 안의 ‘추천 문구 만들기’를 누르면 AI 추천을 생성한다. 닫았다 열어도 추천과 편집 내용은 남는다.

## 35. 공개 결과 조회 기간과 진행 표시 [DML-20261126-151]

- 분실물 찾기와 직접 찾기 검색 결과는 최근 2개월 또는 적용한 기간을 표시한다. 출처별 페이지를 모두 확인했을 때만 공개 목록 확인 완료로 표시한다. 사진·설명 비교 진행은 공개 목록 조회와 구분한다.
- 기존 후보 아래에서 이어 찾을 수 있다. 분실물 결과는 ‘공개 목록 더 확인’, 직접 찾기는 ‘더 찾아보기’를 사용한다. 직접 찾기 일반 검색의 추가 조회는 텍스트 목록만 진행하며 로봇 애니메이션은 AI 검색에 사용한다.

## 36. 파이프라인 AI 모델 맵 [DML-20261127-152]

- 개발용 확인실의 노드 흐름 지도에서 모델 이름과 가중치, 사용 여부, 연결된 단계를 한 번에 확인할 수 있다. 검색 경로가 확인되지 않은 보유 모델은 별도로 표시한다.

## 37. 파이프라인 홈 테스트 정보 [DML-20261127-153]

- 파이프라인 홈에 실행일 기준 전체 자동 테스트 통과 수, 검색 기능별 합성 검증 결과, 실제 공개 API·AI 표본을 표시한다.

## 38. 파이프라인 별도 테스트 메뉴 [DML-20261127-154]

- 37번의 테스트 정보는 별도 ‘테스트’ 메뉴에서 열 수 있다. 실제 실행한 검색마다 검색어, 조건, 첨부, 원본 캡처를 기록한다. 데스크톱의 캡처 오른쪽에서 상위 5개의 실제 원점수, 점수 산정식과 평균을 확인할 수 있다.
- 0건은 빈 순위와 평균으로 표시한다. 공개 목록 일부 확인과 사진 비교 실패를 함께 기록하고, 합성 회귀 테스트는 실제 검색 사례와 별도 영역에서 확인한다.

## 39. 파이프라인 홈 검색 구조 요약 [DML-20261127-155]

- 홈 상단은 검색 방식별 한 줄 설명과 공통 공개 검색 범위로 구성한다. 목록 아래에 공개 출처, 기본 기간인 최근 2개월, 남은 목록 이어 조회를 표시한다.

## 40. 자연어 분실일 조회 범위 확대 [DML-20261127-156]

- 분실물 찾기와 직접 찾기 AI에서 자연어 날짜 또는 기간이 확인되면 해당 첫날의 10일 전부터 한국 시간 기준 오늘까지 공개 목록을 확인한다. 6개월 상한이 걸리면 확대된 시작일을 기준으로 최대 6개월까지만 본다.
- 직접 적용한 기간 필터가 우선이다. 날짜 단서가 없으면 최근 2개월이 기본이다. 결과에서는 실제 조회 기간과 공개 목록의 확인 상태를 표시한다.

## 41. 첫 인덱스 표지 [DML-20261127-157]

- 루트 `/`는 브랜드 표지를 연다. ‘분실물 찾기’는 `/lost-found`, ‘갤러리에서 사진 찾기’는 `/gallery`로 연결한다. 기존 모드 탭과 검색 입력은 해당 검색 페이지에 둔다.
- 종이색, 먹색, 적갈색과 휴대폰 형태의 검색 예시는 표지의 시각 검토안이다. 나머지 화면에 적용할 스타일은 표지를 확인한 뒤 확정한다.

## 42. 웹앱 공통 브랜드 스타일 [DML-20261127-158]

- 사용자가 승인한 표지의 종이색·먹색·적갈색을 웹앱 전체에 적용한다. 주요 행동과 선택 상태에 적갈색을 사용하고 사진 배경·보조 정보를 종이색 계열로 구분한다.
- 검색 대상은 검색 입력 위에, 연결한 갤러리 미리보기는 입력 아래에 둔다. 모바일 360px 이상에서는 ‘사진 첨부’와 검색 버튼을 같은 줄에 표시한다.
- 분실물 결과의 실제 조회 범위와 남은 목록 확인은 한 영역에 둔다. 직접 찾기 데스크톱은 검색 방식·검색창·검색 버튼을 한 줄에 둔다. 상태 안내, 보관기관 정보와 사진 처리 안내를 각 행동과 가까운 위치에서 확인할 수 있다.
- 찾은 기록·북마크, 보관함과 등록 폼, 로그인·설정·계정·오류 화면은 같은 버튼·제목·표면 기준을 사용한다. 사진 첨부에는 AI로 만든 우산 예시임을 표시한다.

## 43. 공통 헤더와 찾은 기록 높이 [DML-20261127-159]

- 표지와 내부 화면은 헤더의 기준 폭과 여백을 공유한다. 내부 화면 배경은 오른쪽 위의 옅은 살구색에서 종이색으로 이어진다.
- 찾은 기록의 데스크톱 두 열에서 같은 줄에 있는 카드의 높이를 맞춘다. 모바일은 한 열에 내용만큼 높이를 둔다. 검색 기록과 북마크 카드는 각각 최대 3건으로 시작하고, 이전 항목은 해당 카드의 더 보기에서 펼친다. 제목 옆에는 전체 건수를 표시한다.

## 44. 디자인 변경안 2 검토 [DML-20261127-160]

- 변경안은 `디자인-변경안2` 브랜치에서 확인한다. 표지와 내부 화면은 기존의 따뜻한 색상과 공통 헤더 위치를 사용한다.
- 검색 입력에는 사진과 문장 예시를 추가한다. 결과 분류의 아이콘, 상세 사진 프레임, 기록 카드의 제목 영역을 보강한다. 검색 조건, 결과 분류 순서, 계정·저장 규칙은 기존 기준을 따른다.

## 45. 두 검색 화면의 입력과 예시 배치 [DML-20261127-161]

- 데스크톱에서 검색 모드 탭, 페이지 제목, 검색 대상이 같은 기준선에서 시작한다. 밝은 입력 예시 카드는 오른쪽에 두고 검색 대상이나 갤러리 연결 영역과 상단을 맞춘다. 좁은 화면은 입력 영역 아래에 가로형 예시 카드를 표시한다.
- 검색 모드 탭 뒤의 표면은 버튼 그룹에 적용한다. 탭 주변의 배경은 헤더와 본문 사이에서 살구색 그라데이션이 이어진다.
- 두 검색 화면의 헤더와 검색 모드 탭 사이에 화면 폭에 따라 8~12px의 여백을 추가한다. [DML-20261127-162]
- 최신 DML-20261127-163은 여백을 검색 화면 헤더 카드 아래에 배치하고 폭에 따라 24~32px로 확대한다.
